# 레거시 이관 프레임워크 리뷰에 대한 판단과 개선 기준

2026-10-09 작성. 이 문서는 전달받은 리뷰를 ScFramework의 제품 목적과 저장소 근거에 대조한 판단이다. 리뷰 당시의 관찰과 이번 다중 DB 개선 작업을 구분한다. 상세 원문은 [레거시 마이그레이션 검토](질의/레거시-마이그레이션-프레임워크-검토.md), 당시 실행 근거는 [검증 요약](검증/2026-10-09-migration-review.json)에 있다.

**리뷰의 핵심 방향에 동의한다.** 공통 UI와 서버 기반은 이미 재사용할 가치가 있지만, 판매용 레거시 이관 프레임워크의 완성도를 예제 화면의 정상 동작만으로 판단할 수는 없다. 고객 개발자가 공통 소스를 수정하거나 복사하지 않고 기존 SQL·인증·트랜잭션을 연결할 수 있어야 한다. 현재 기반을 유지하면서 DB 차이와 이관 절차를 제품의 공식 계약으로 만드는 것이 적절하다.

다만 리뷰의 모든 항목을 현재 발생한 장애나 보안 취약점으로 읽어서는 안 된다. Windows의 검사 누락과 POSIX API 호출은 재현 근거가 있는 결함이다. 다중 DB의 SQL·트랜잭션 차이는 코드에서 확인한 이식성 문제다. EJB의 분산 트랜잭션, 기존 인증 연동, 신구 시스템 동시 쓰기는 고객의 실제 구성에 따라 판단해야 하는 이관 조건이다. 실제 고객 DB와 레거시가 없는 상태에서 그 환경의 동작을 보장하거나 실패했다고 단정할 수는 없다.

## 2. 주요 지적에 대한 판단

### 2.1 DB 교체에 공통 코드 수정이 필요할 수 있다는 지적

가장 먼저 구조적으로 보완할 항목이다. 리뷰 시점의 [JdbcMessageStore](../backend/framework-autoconfigure/src/main/java/dev/scframework/autoconfigure/messaging/JdbcMessageStore.java), [OperationalSchedulerService](../backend/framework-autoconfigure/src/main/java/dev/scframework/autoconfigure/scheduling/OperationalSchedulerService.java), [BrowserErrorService](../backend/framework-autoconfigure/src/main/java/dev/scframework/autoconfigure/browsererrors/BrowserErrorService.java)에 행 제한 SQL이 직접 들어 있었다. 생성 앱 [bootstrap-api.mjs](../templates/starter-v2/scripts/bootstrap-api.mjs)는 임시 H2 서버로 API 명세를 수집했다. 이 경로들은 고객 DB 전용 migration·SQL을 추가할 때 함께 검토해야 한다.

문제는 H2를 개발 기본값으로 사용하는 것 자체가 아니다. 빠르게 실행할 수 있는 기본값은 유지할 수 있다. 문제는 그 기본값의 문법과 동작이 공통 서비스의 전제까지 되는 것이다. JPA가 DB 방언을 선택하더라도 직접 작성한 JDBC/MyBatis SQL, Flyway DDL, Quartz 저장소, UUID·시간·생성 키 처리를 모두 대신 변환하지는 않는다.

예를 들어 Oracle과 SQL Server의 행 제한 구문은 해당 DB의 규칙을 따라야 하며, 안정적인 페이지 조회에는 정렬 기준도 필요하다. [Oracle SELECT 문서](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/SELECT.html), [SQL Server ORDER BY 문서](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-order-by-clause-transact-sql?view=sql-server-ver17)가 이를 설명한다. 또 PostgreSQL에서는 SQL 오류로 중단된 트랜잭션을 Java `catch`만으로 계속 사용할 수 없다. rollback이나 savepoint 복구 등 명시적인 전략이 필요하다. 따라서 중복 삽입을 잡고 같은 트랜잭션에서 합산하던 H2 기준 코드는 충돌 처리까지 바꿔야 한다. 이는 코드와 [PostgreSQL 트랜잭션 문서](https://www.postgresql.org/docs/18/tutorial-transactions.html)를 대조한 판단이며, 리뷰 당시 실 PostgreSQL에서 재현한 결과는 아니다.

공통 기능의 DB 차이는 프레임워크가 제공하는 방언·저장소 어댑터와 DB별 예제 DDL에서 처리해야 한다. 고객의 기존 테이블·키·프로시저·업무 규칙은 소비 앱의 Mapper/Repository/Service에 둔다. 이 경계를 만들면 고객마다 공통 소스를 수정하는 부담을 줄일 수 있다. “다른 DB는 불가능하다”는 결론보다 “공식 연결 계약과 검증이 부족했다”가 정확하다.

### 2.2 EJB 이관 시 트랜잭션 의미가 달라질 수 있다는 지적

위험 판단에 동의하되, 모든 EJB 업무가 XA를 사용한다고 가정하지 않는다. 단일 DB의 로컬 트랜잭션, 여러 자원이 참여하는 CMT/JTA, 원격 EJB, 메시징과의 연계는 각각 실제 구성을 확인해야 한다. 현재 같은 DataSource에서 JPA 변경을 flush하고 MyBatis로 읽는 예제는 로컬 트랜잭션의 좋은 기반이다. 이 예제로 분산 트랜잭션까지 검증했다고 볼 수는 없다.

우선 제공할 이관 예제는 두 가지다. 첫째, 기존 EJB 안에 한 업무의 트랜잭션을 유지하고 새 서버는 명시적인 gateway를 통해 결과를 받는다. 둘째, 함께 성공하거나 실패해야 하는 업무 전체를 새 Service의 트랜잭션으로 옮긴다. 기존 구성상 XA가 필요하면 자원 참여와 트랜잭션 매니저 설정을 별도로 구현·검증한다. Spring은 JTA를 지원하며, 구체적인 자원 구성은 [Spring 6.2 트랜잭션 전략 문서](https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/strategies.html)를 따른다.

일반적인 HTTP/Feign 호출과 로컬 `@Transactional`만으로 원격 서버의 커밋이 함께 rollback되지는 않는다. HTTP timeout도 상대방 미처리의 증거가 아니다. 원격 연결 예제에는 요청 식별, 중복 방지, 결과 조회, 재시도 조건을 포함해야 한다. 현재 outbox는 유용하지만 기존 XA의 원자성 의미를 자동으로 대체한다고 설명해서는 안 된다.

### 2.3 기존 인증과 URL을 붙일 때 보호가 빠질 수 있다는 지적

리뷰 시점의 [기본 보안 설정](../backend/framework-autoconfigure/src/main/java/dev/scframework/autoconfigure/ScSecurityAutoConfiguration.java)은 `/api/**`를 인증 대상으로 하고 나머지 경로를 허용했다. SPA의 화면·정적 자산에는 필요한 구성이지만, `/legacy/export.do` 같은 별도 업무 Controller를 추가하면 인증 범위에 포함되는지 확인해야 한다. 이는 GET 업무 URL 등에서 발생할 수 있는 구체적인 이관 위험이다. 해당 경로에 실제 취약 endpoint가 있다는 보고는 아니다. CSRF를 사용한다는 사실도 읽기 업무의 인증 검사를 대신하지 않는다.

보완 방향은 공개 화면·정적 자산 경로와 보호할 업무 경로를 명시하는 공식 확장점을 제공하고, 미인증 401·무권한 403·CSRF 실패를 시험하는 것이다. 소비 앱이 전체 SecurityFilterChain을 교체해야 하는 경우에도 세션·CSRF·오류 JSON·로그아웃 계약을 보존하는 예제가 필요하다. 임의 경로를 모두 열어 놓은 채 개발자 기억에 의존하는 방식은 줄여야 한다.

기존 사용자 테이블 연결은 `UserDetailsService` 확장점에서 시작할 수 있다. 이후 사번·조직·복수 권한·비밀번호 검증·계정 상태·권한 변경과 세션 만료를 묶은 예제가 필요하다. 같은 쿠키 이름만으로 구형 WAS와 새 서버의 세션이 공유되지는 않는다. 세션 병행 정책과 서버 간 신뢰 경계는 고객별 어댑터의 계약으로 다룬다. 이 개선을 위해 Redis·JWT·SSO를 기본으로 도입할 필요는 없다.

### 2.4 폼과 비동기 처리의 반복 코드에 대한 지적

공통화 필요성에 동의한다. 리뷰 시점의 [useDraftGuard](../frontend/apps/reference-app/src/shared/useDraftGuard.ts)는 일반적인 미저장 입력 보호 기능이면서 Reference 인증 모듈을 참조했다. 생성 앱의 [NotesPage](../templates/starter-v2/frontend/src/features/notes/NotesPage.vue)는 별도의 이동 확인, Zod 검증 연결, mutation과 조회 갱신을 구현하고 있었다. 화면 수가 늘면 버그 수정과 사용성이 서로 달라질 수 있다.

공통 패키지는 미저장 확인, `safeParse` 결과와 서버 필드 오류 연결, 저장 후 Query 갱신, 선택 변경 시 늦은 응답 폐기, 충돌 시 입력 보존을 조합할 수 있는 작은 composable로 제공하는 편이 적절하다. 세션 상태는 앱의 Reference 모듈을 import하지 않고 runtime 계약 또는 명시적으로 전달받은 값으로 연결한다. 공개 패키지를 실제로 소비하는 최소 앱으로 재사용 가능성을 확인해야 한다.

업무 필드와 검증 규칙, 변경 가능한 상태, 서버 권한과 revision의 의미는 앱이 소유한다. Router·Vue Query·폼·computed·Pinia의 상태 소유권도 유지한다. 공통화 때문에 모든 화면을 한 형태의 CRUD 컴포넌트에 맞추거나 업무 권한을 공통 패키지에 넣는 방향은 피한다.

### 2.5 앱 생성 이후 업무 개발 지원이 부족하다는 지적

제품 목적에 맞는 다음 개발 과제다. 프로젝트 생성기는 시작 비용을 줄이지만, 거래처·발주·재고 같은 기능을 추가하는 반복 비용까지 줄이지는 못한다. 업무 기능 생성은 검색·목록·상세·폼·API 타입 연결·라우트·Controller/Service·검증·권한·409·기본 테스트를 한 흐름으로 제공해야 한다. 생성 이후 코드는 고객 개발자가 이해하고 수정할 수 있어야 하며, 재생성이 고객의 수정본을 무조건 덮어쓰면 안 된다.

신규 테이블을 만드는 JPA 예제와 기존 SQL·프로시저를 보존하는 MyBatis/JDBC 예제는 진입 경로를 나누는 것이 좋다. 같은 세션·오류·권한·트랜잭션 계약을 사용하되, 첫 업무를 옮기기 위해 모든 조회 기술을 동시에 이해할 필요는 줄인다. 이는 기존의 조건부 기술 구현 범위를 축소하자는 뜻이 아니다. 프레임워크가 제공하는 기능과 소비 앱이 처음 선택하는 기능을 구분하자는 것이다.

기능 생성기는 DB 연결 기반을 먼저 정리한 뒤 구현해야 한다. H2 전용 migration과 현재 반복 코드를 그대로 대량 생성하면 이관 비용까지 반복 생산하게 된다.

### 2.6 Windows 결함과 생성 앱 검증에 대한 지적

두 결함 모두 수용해야 한다. 당시 [의존성 검사기](../scripts/check-ui-boundaries.mjs)는 OS가 반환한 경로와 `/`를 붙인 문자열을 비교해 Windows에서 소속 판정이 빠졌다. 수정의 완료 기준은 실제 Windows에서 정상 공개 import는 허용하고, 비공개 내부 참조·공통→업무 앱 참조·업무 앱 간 참조를 모두 거절하는 것이다. 로그에 검사한 import 수가 출력됐다는 사실만으로 규칙이 실행됐다고 판단하면 안 된다.

생성 앱 테스트의 `Files.setPosixFilePermissions`는 지원하는 파일 속성 뷰를 확인하고 Windows의 접근 제어 방식을 다뤄야 한다. JDK 21도 POSIX 속성 뷰를 지원하지 않는 파일시스템에서는 이 호출이 `UnsupportedOperationException`을 던진다고 명시한다. [JDK Files 문서](<https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/file/Files.html#setPosixFilePermissions(java.nio.file.Path,java.util.Set)>). 예외를 무시하거나 파일을 광범위하게 읽을 수 있게 만들어 테스트만 통과시키는 것은 적절한 수정이 아니다.

루트 Windows 개발 실행기의 성공과 판매하는 생성 앱의 성공은 별도 기준이다. 생성 앱에서 새 경로 생성→패키지 설치→프런트 빌드→Java 테스트→JAR 실행→로그인·CSRF·CRUD→종료를 독립적으로 검증해야 한다. 임시 계정과 DB를 사용하고 실제 `.runtime/dev`를 테스트에 사용하지 않는다.

### 2.7 기존 데이터와 신구 동시 수정 표준에 대한 지적

고객 검증이 필요한 핵심 이관 조건이다. 숫자 ID·revision 예제는 공통 프레임워크의 유일한 업무 모델이 되어서는 안 된다. 문자열 사번, 복합 키, 큰 정수, sequence·trigger·프로시저, 금액·날짜·null과 빈 문자열의 의미를 소비 앱에서 보존해야 한다. 기존 키를 새 번호로 임의 변환하면 다른 테이블과 첨부·감사 연결도 함께 검증해야 한다.

새 시스템만 revision을 올리고 기존 JSP는 같은 행을 그대로 변경하면, 새 시스템의 revision 비교로 그 변경을 감지하지 못할 수 있다. 우선 업무별 쓰기 주체를 정하고 기능 단위로 전환한다. 동시 쓰기가 필요하면 구형 경로까지 포함한 변경 번호·잠금·변경 감지 계약을 설계한다. 새 서비스에 `@Version`을 추가하는 것만으로 해결됐다고 판단하지 않는다.

대표 업무의 동일 입력에 대해 조회 결과뿐 아니라 DB 변화·권한·오류·반올림·날짜·첨부 해시·commit/rollback을 비교해야 한다. 고객 DB에 Flyway를 도입할 때 기존 schema의 변경 권한과 baseline을 먼저 정하고, 신규 예제 DDL을 기존 업무 schema에 그대로 적용하지 않는다.

## 3. 이번 다중 DB 개선의 범위와 완료 기준

이번 요청은 **H2 기본 개발 경로를 유지하면서 Oracle·Db2·Microsoft SQL Server·PostgreSQL을 선택할 수 있는 프로젝트로 확장하는 것**이다. 한 앱이 사용할 DB 제품을 선택하는 기능과 여러 DB를 동시에 사용하는 기능은 다르다. 전자는 이번 DB 기반 개선의 대상이며, 후자의 복수 DataSource·XA·분산 업무는 별도 이관 설계와 시험이 필요하다.

| 계층           | 프레임워크가 제공할 것                                                                  | 소비 앱이 소유할 것                                          |
| -------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 접속           | DB 선택, 드라이버와 필요한 모듈, URL·사용자·비밀정보 연결 방법, 잘못된 조합의 시작 거절 | 실제 주소·계정·TLS·schema·배포 환경                          |
| 공통 SQL       | 행 제한, UUID·시간·생성 키 등의 JDBC 경계, 중복 충돌 시 트랜잭션 처리                   | 기존 업무 SQL·프로시저·키·DB별 성능 튜닝                     |
| migration      | 지원 DB별 공통 기능 DDL 예제와 선택 규칙                                                | 실제 migration 파일·순서·기존 checksum·적용 승인과 변경 권한 |
| 선택 운영 기능 | 메시징 저장소·스케줄러·오류 수집·감사의 DB별 계약과 검증 경로                           | 활성 여부·보존 정책·업무 메시지와 작업                       |
| 생성 앱        | 선택 DB의 설정·예제·명세 수집 절차와 독립 빌드 경로                                     | 고객 기능·권한·데이터 이관·배포                              |
| 검증           | DB별 재실행 가능한 계약 테스트와 명령                                                   | 고객 버전·데이터·WAS에서의 수락 시험                         |

지원 DB 이름을 설정에 추가한 것과 실제 지원 검증 완료는 구분한다. Oracle은 버전과 호환성 수준, Db2는 LUW·z/OS·IBM i 중 제품군, SQL Server는 버전과 호환성 수준, PostgreSQL은 주요 버전을 특정해야 한다. 특히 `db2`라는 설정 이름만으로 모든 Db2 제품군을 검증했다고 설명해서는 안 된다.

최소 수락 시험은 다음과 같다.

1. 새 임시 schema에서 앱 소유 migration을 적용하고 재시작 시 같은 이력을 유지한다. 기존 H2 migration의 checksum과 실행 자료를 보존한다.
2. JPA 쓰기→flush→MyBatis 조회가 같은 DataSource/트랜잭션에서 일치하고, 중간 실패 시 DML을 함께 rollback한다. DDL의 commit 동작은 별도로 기록한다.
3. 목록 정렬·페이지 경계·한글·긴 문자열·UUID·시간·생성 키·revision 충돌과 금액의 정밀도를 확인한다.
4. 운영 기능 ON에서 메시지 중복·outbox/inbox·예약·브라우저 오류 중복 접수와 동시 합산을 검증한다. OFF 상태에서 해당 테이블이나 외부 서비스가 필요하지 않은지도 확인한다.
5. 생성 앱의 선택 DB 설치·빌드·API 타입 생성·JAR 시작과 기본 CRUD를 확인한다. 검증된 OpenAPI 파일을 사용하는 경로가 있다면 실제 서버 명세와의 일치도 별도로 확인한다.
6. H2의 호환 모드나 SQL 문자열 단위 테스트 결과와 실제 Oracle/Db2/SQL Server/PostgreSQL 실행 결과를 구분해 기록한다. 외부 DB 엔진을 실행하지 못한 경우는 미확인으로 남긴다.

### 이번에 반영한 구현

접속 문자열만 추가하는 수준을 넘어 다음을 수정했다. 선택 방법과 DB별 선행조건은 [DB 가이드](database-support.md)를 따른다.

- 공통 Starter의 강제 H2 runtime 의존성을 제거하고 Reference·Starter·생성 v2 POM에 DB별 JDBC/Flyway profile을 추가했다. 외부 DB profile에서 H2는 테스트에만 남는다.
- 앱 2개와 생성 v2에 DB 설정 15개와 외부 DB migration 56개를 추가했다. 기존 H2 SQL 14개는 checksum을 보존했다. Oracle 빈 문자열·예약어, Db2 LUW Unicode/CLOB·UTC, SQL Server Unicode/IDENTITY, PostgreSQL 긴 문자열 매핑을 함께 다뤘다.
- 공통 `DatabaseDialect`와 교체 가능한 bean을 제공했다. 페이징·시각·UUID·Quartz delegate를 분리하고, 중복 INSERT는 같은 연결의 savepoint로 복구해 이전 업무 DML과 최종 rollback 책임을 유지한다. Flyway 실행 전 선택 vendor와 실제 연결 DB가 다르면 거절한다.
- Windows/Linux 개발 실행과 생성 앱에서 vendor를 선택할 수 있다. API 타입은 명시적인 명세 파일 또는 loopback 서버에서도 생성하여 외부 DB 빌드가 임시 H2를 강제하지 않게 했다.
- Windows 의존성 검사 경로, 생성 앱의 합성 secret 권한, API/UI 계약 검사기의 CRLF·경로 구분자 오탐을 수정했다. 기존 생성 타입과 UI snapshot은 변경하지 않았다.
- 정적 설정 게이트와 외부 DB의 빈 전용 schema를 사용하는 opt-in 계약 시험을 추가했다. 실제 외부 계정·DB를 자동으로 가정하거나 실행하지 않는다.

전체 검증의 실패도 남긴다. `scripts/build.sh`는 실행 중 Sass 파일의 Windows 잠금 때문에 `npm ci`에서 중단됐다. 같은 잠긴 패키지의 파일을 복원하고 `npm install`을 완료했으며 lock의 의미 변경은 없지만, 이를 `npm ci` 성공으로 대신 표시하지 않는다. 전체 형식 검사는 기존 `.runtime/windows-check/secrets` 접근 권한 때문에 디렉터리 탐색에서 중단됐고, 변경한 JS/새 문서의 scoped 형식 검사는 통과했다.

처음 전체 Maven 실행에서는 기존 Unix `lockf` 1개와 Windows 심볼릭 링크 권한 3개가 실패했다. 해당 테스트 소스의 검증을 약화하지 않고 후속 명령에서 네 메서드를 제외하여 나머지 회귀를 확인했다. 일반 target의 패키징은 실행 중 JAR 잠금으로 실패하여 별도 소스 복사 경로에서 새 JAR를 만들었다. 새 외부 DB 시험의 제네릭 타입 추론 컴파일 오류도 수정 후 Starter에서 컴파일·기본 skip을 확인했다.

추가로 기본 H2 지연 쓰기와 Windows 강제 종료의 조합에서 최근 변경 손실을 재현했다. 테스트 URL에만 `WRITE_DELAY=0`을 추가한 명시적 `--h2-write-through` 시험은 17개를 통과했지만, 기본 설정의 정상 종료나 전원 장애 무손실을 확인한 결과는 아니다. 이 경계와 재실행 명령은 [DB 가이드](database-support.md)에 기록했다.

최종 독립 검토에서는 Oracle EXTENDED의 장문 CLOB·선택 열 NULL, SQL Server JSON의 nationalized 매핑 불일치를 추가로 찾아 수정했다. 실제 Hibernate metadata를 사용하는 [새 검사 4개](검증/2026-10-09-database-orm-mapping.json)가 통과했다. 수정 후 H2 문서/요구사항 27개와 metadata 4개를 합친 31개 재검증 및 Reference JAR 재패키징도 통과했다. 기존 213개와 겹치는 27개를 새 성공 개수로 중복 합산하지 않는다. 외부 DB 연결 없는 metadata 검사는 실제 DB의 DDL·JDBC 검증을 대신하지 않는다.

실제 Oracle·Db2 LUW·SQL Server·PostgreSQL 서버 실행, 고객 schema와 데이터 이관, 외부 DB backup/restore, EJB/XA, 구형 인증, 신구 동시 쓰기는 **미확인 또는 후속 구현 대상**이다. 설정·DDL·공통 경계·패키징 구현을 실 DB 제품 인증 완료로 표시하지 않는다.

## 4. 개선 우선순위와 제품 완성도 판단

사용자가 제시한 개선 순서는 대체로 타당하다. 다만 고객의 모든 환경 정보가 도착할 때까지 확인된 결함 수정과 DB 확장점 설계를 멈출 필요는 없다. 공통 기반을 먼저 정리하고, 실제 지원 버전·WAS·기존 인증·EJB 범위는 고객 적용 전에 확정한다.

| 우선순위 | 작업                                               | 완료를 판단할 근거                                                           |
| -------- | -------------------------------------------------- | ---------------------------------------------------------------------------- |
| 1        | 확인된 Windows 결함 수정과 업무 URL 보호 계약 보완 | 금지 의존성 거절, 권한 파일 처리, 비API 업무 URL의 인증·권한 시험            |
| 2        | 다중 DB 연결·SQL·DDL·생성 경로 정리                | DB별 구성과 공통 계약 시험, 실행 DB·버전·미확인 범위를 담은 지원표           |
| 3        | 기존 계정·서비스·SQL 연결 예제                     | 고객 공통 소스 수정 없이 계정·프로시저·기존 트랜잭션 연결                    |
| 4        | 공통 폼 로직과 업무 기능 생성                      | Reference import 없이 목록·상세·입력·오류·409·이동 보호와 기본 시험을 재사용 |
| 5        | 실제 JSP/EJB 대표 업무 이관                        | 익명화한 동일 사례의 신구 결과·DB 변화·권한·트랜잭션 비교                    |
| 6        | 고객 앱 독립 설치·업그레이드·복구                  | 지원 OS·DB에서 새 설치, 고객 수정 보존, DB 변경 및 업무 데이터 복구 확인     |

1~6의 후속 과제를 이번 DB 변경 하나로 모두 완료 처리하지 않는다. 기능 생성기·기존 인증/EJB 예제·실제 고객 이관은 각각 구현과 수락 시험을 따로 가져야 한다. 기존 001~012의 구현 이력은 보존하고, 해당 단계의 확장과 후속 제품화 작업으로 추적한다.

앞으로의 완료 기준은 “예제가 동작하는가”와 함께 “공통 소스를 건드리지 않은 독립 앱에서 대표 레거시 업무를 이관할 수 있는가”, “고객 변경을 보존하며 패치·DB 변경·복구를 수행할 수 있는가”여야 한다. 공통 패키지 분리, 세션 변경 시 요청·캐시 정리, CSRF, 서버의 최종 권한 검사, 소비 앱 확장점은 이 목표를 위한 자산이다. 이 기반 위에서 반복 개발과 이관의 실제 비용을 줄이는 방향으로 제품을 완성하는 것이 적절하다.
