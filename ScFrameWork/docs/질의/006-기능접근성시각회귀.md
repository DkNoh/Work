# 006 기능·접근성·시각 회귀

상태: **구현·로컬 통합 검증 완료**. 새 두 앱 JAR에서 전체 기능/접근성 26개와 별도 시각 비교 4개를 통과했다. 원격 CI와 Linux 시각 프로필은 아직 실행하지 않았다. 현재 확인한 로컬 환경은 macOS 26.6.2이며 Docker CLI는 있으나 daemon 연결이 되지 않아 Linux 기준 이미지를 만들지 못했다. VoiceOver의 실제 음성 안내와 전체 WCAG 수동 심사는 미실시다.

사용자가 요청한 모든 조건부 기술도 구현·예제·기능 검증 대상이다. Redis·JWT·SSO는 제외하고 세션·CSRF를 유지한다. WorkboardVue는 읽기 전용 레퍼런스다. 공통 UI의 `Sc`/`sc-*`, Vue SFC, 상태 원본, H2, OpenFeign 계약은 001~005를 그대로 따른다.

## 작은 대표 이미지 세트

이미지 이름은 업무 자료가 아닌 공통 UI의 재사용 부위를 나타낸다. 두 앱의 독립적인 `/patterns` 기능 폴더가 각각 공통 패키지를 소비하며 서로 다른 앱 코드를 import하지 않는다. `ScSectionCard`의 실제 `<section aria-labelledby="…">`는 내부 제목 `<h2 id="…">`로 이름을 갖는 region이다. 표/차트/서식 캡처는 각각 실제 한국어 제목 `정렬·페이지·선택 예제`, `중립 차트`, `서식 입력`을 exact name으로 조회한다.

| 앱        | viewport   | 비교 이미지 4장                                           | 고정 자료                                                                     |
| --------- | ---------- | --------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Reference | 1366 × 844 | `reference-1366-shell-inputs`, `table`, `chart`, `editor` | 합성 admin 세션, 한국어 입력 초안, 표 첫 10행, A/B/C = 12/24/18, JSON 첫 문단 |
| Reference | 390 × 844  | `reference-390-shell-inputs`, `table`, `chart`, `editor`  | 같은 자료, 닫힌 모바일 메뉴                                                   |
| Starter   | 1366 × 844 | `starter-1366-shell-inputs`, `table`, `chart`, `editor`   | 로그인 없이 독립 Starter `/patterns`, 같은 합성 자료                          |
| Starter   | 390 × 844  | `starter-390-shell-inputs`, `table`, `chart`, `editor`    | 같은 자료, 닫힌 모바일 메뉴                                                   |

총 4개 테스트, 16개 PNG다. 셸·입력은 첫 viewport만, 표·차트·서식은 각 `ScSectionCard` 영역만 비교한다. 10,000행 전체나 전체 페이지를 긴 이미지로 저장하지 않는다. 가상 표의 DOM 수·중간/마지막 행·선택·focus 보존은 `patterns.spec.ts`의 실제 기능 검사가 맡는다. 입력 오류·busy·readonly·disabled·빈 표/차트·대화상자는 해당 Story의 기능/axe 검사를 먼저 유지하며, 시각 세트 확장은 실제 발견한 회귀의 재현 화면부터 추가한다.

입력 값은 `시각 기준 한국어 제목`, 두 줄 설명, 분류 `개발`, 확인 checkbox 선택으로 고정한다. 저장 동작으로 자료를 생성하지 않는다. 차트 종류는 첫 막대 그래프, 데이터 표 details는 닫힘, 서식의 JSON details도 닫힘이다. 앱 로컬 fixture와 JAR 화면을 사용하고 원격 API·사용자 DB·사용자 업로드는 사용하지 않는다. 로그인은 기존 E2E harness가 생성한 임시 비밀번호 파일을 읽으며 값은 로그·문서·캡처에 넣지 않는다.

| `SC_VISUAL_PROBE=1`                                | 셸 브랜드 색/모서리를 고의로 변경하는 실패 probe. 기준 갱신과 동시 사용 금지                             |

`manifest.json`은 프로필·실제 환경·케이스 계약·이미지 크기/해시를 함께 보관한다. OS 정보는 Node의 `os.release()`와 `os.version()`을 실제 측정한다. 커널/OS 업데이트도 승인 환경 변경으로 감지하므로, 업데이트 후에는 같은 환경에서 이미지를 다시 검토해야 한다. `--record`는 해당 새 run-id의 네 case가 모두 완료한 증거와 정확한 16장을 확인한다. 기본 verifier는 기준 파일을 수정하지 않는다. 이미지 파일을 바꾸고 manifest를 갱신하지 않으면 실패한다. 다만 manifest는 승인 서명이나 암호학적 배포 신뢰 체계가 아니므로 이미지+manifest 변경을 코드 리뷰에서 함께 승인해야 한다.

## 처음 만들고 비교하는 순서

새 프런트가 포함된 두 Spring JAR가 먼저 필요하다. 기존 기능 E2E와 시각 E2E의 webServer는 같은 포트·metadata를 소유하므로 **동시에 실행하지 않는다**. 저장소 루트에서 실행한다. 현재 macOS에서는 `CHROME_BIN`으로 로컬 Chrome을 선택할 수 있고, 그 경우 Playwright 내려받은 Chromium과 별개의 환경으로 기록된다.

```sh
# 루트가 새 두 앱 JAR와 기능 E2E를 확인한 뒤 순차 실행
SC_VISUAL=1 SC_VISUAL_PROFILE=darwin-chromium SC_VISUAL_UPDATE=1 \
SC_VISUAL_RUN_ID=006-next-approved \
CHROME_BIN='/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' \
npm run test:e2e -- visual.spec.ts --update-snapshots=all

node scripts/verify-visual-baselines.mjs \
  --profile darwin-chromium --record --run-id 006-next-approved

node scripts/verify-visual-baselines.mjs --profile darwin-chromium

SC_VISUAL=1 SC_VISUAL_PROFILE=darwin-chromium \
CHROME_BIN='/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' \
npm run test:e2e -- visual.spec.ts --update-snapshots=none
```

이 첫 생성 명령은 초기 기준 이미지 준비를 위한 명시 동작이다. 생성 후 16장을 사람이 확인하고 README/단계 체크를 마감하는 담당자에게 전달한다. 이후 일반 비교 명령은 `--update-snapshots=none`을 강제하므로 누락한 기준 이미지를 Playwright 기본 `missing` 모드로 자동 생성하지 못한다. 최초 실행·비교 결과와 이미지 검토를 모두 기록한 뒤 기준 파일을 저장한다.

고의 회귀도 한 번 검증한다. 다음 명령은 **exit 1이 정상 기대값**이며 첫 셸 이미지의 actual/diff를 남겨야 한다. 비교 전후 manifest/PNG 해시가 그대로인지 기본 verifier로 확인한다. 실패 probe를 일반 CI 성공 단계로 넣지 않는다.

```sh
SC_VISUAL=1 SC_VISUAL_PROFILE=darwin-chromium SC_VISUAL_PROBE=1 \
CHROME_BIN='/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' \
npm run test:e2e -- visual.spec.ts --update-snapshots=none --max-failures=1

node scripts/verify-visual-baselines.mjs --profile darwin-chromium
```

## 변경 시 기준 갱신

1. 일반 비교 실패의 actual/expected/diff를 먼저 확인한다. 폰트 미준비·lazy render·실제 제품 회귀와 환경 변경을 구분한다.
2. 디자인 변경이면 토큰/공통 UI 계약·두 소비 앱·Story의 기능/axe를 먼저 확인하고 변경 의도를 PR에 적는다.
3. 같은 승인 환경에서 새로운 run-id와 명시 update 명령을 사용한다. 새 16장과 manifest를 함께 검토한다.
4. 환경/브라우저가 바뀌면 해당 환경에서 새 승인 세트를 만든다. Mac 이미지를 Linux 파일명으로 복사하지 않는다.
5. 일반 compare를 다시 실행해 4개 case가 통과하고, verifier가 16개 해시를 확인하는지 기록한다. 기존 이미지를 무조건 덮어쓰는 재시도 스크립트는 만들지 않는다.

## CI 연결과 실패 처리

기본 `.github/workflows/verify.yml`은 빌드·서버·Catalog 기능/axe·Docs·두 앱 기능 E2E를 유지한다. Linux 기준 이미지가 없다는 이유로 기본 workflow를 실패시키지 않으며 시각 비교의 원격 통과를 뜻하지 않는다. 수동 전용 [visual.yml](../../.github/workflows/visual.yml)을 별도로 작성했다. 현재 **Linux 승인 baseline 미생성·시각 workflow 원격 미실행**이다. Mac 이미지를 Linux profile로 복사하거나 이름만 바꾸어 사용하지 않는다.

| 항목              | 실제 workflow 계약                                                                                                                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| trigger·권한      | `workflow_dispatch`만. push/PR 자동 실행 없음. `contents:read`, `actions:read`, checkout credential 저장 안 함                                                                                                      |
| `baseline_run_id` | 필수 string. 같은 repository에서 승인 artifact를 만든 실행 ID. 양의 숫자·JS safe integer 검사(v4가 내부 parseInt를 사용)                                                                                            |
| `artifact_name`   | 필수 string. `[A-Za-z0-9][A-Za-z0-9._-]{0,99}`의 정확한 이름. slash·공백·glob·빈 이름 제외                                                                                                                          |

`download-artifact@v4`는 token/repository/run-id를 사용해 다른 실행의 artifact를 찾고, 이름 하나를 지정하면 해당 path에 바로 추출한다. v4로 업로드한 immutable artifact를 사용한다. 액션의 archive digest 불일치 안내만으로 job 실패를 보장하지 않으므로 workflow가 사용자가 검토한 **manifest digest를 별도로 강제 검사**하고 verifier가 그 manifest의 PNG hash를 검사한다. 이 해시는 승인 서명/리뷰를 대신하지 않는다. [v4 inputs](https://raw.githubusercontent.com/actions/download-artifact/v4/action.yml), [v4 실제 다운로드 소스](https://raw.githubusercontent.com/actions/download-artifact/v4/src/download-artifact.ts), [v4 artifact 사용·제한](https://raw.githubusercontent.com/actions/upload-artifact/v4/README.md)

`ubuntu-24.04` label만으로 동일 kernel·브라우저·폰트를 보장하지 않는다. 현재 정책은 `os.release()`/`os.version()`의 마이너/커널 업데이트도 환경 차이로 실패시킨다. 이미지 차이를 자동 승인하지 않으려는 의도적인 검수 조건이며 다른 실행 환경에서 비교하려면 승인 세트를 새로 검토해야 한다. Linux 승인 프로필은 해당 CI와 실제로 일치하는 환경에서 생성해야 한다. Docker daemon 또는 고정 runner를 사용할 수 있을 때 루트 담당자와 생성·보관부터 조율한다.

로컬 YAML/inline Node 문법·입력/manifest 실패 조건 확인은 원격 실행 성공을 뜻하지 않는다. 실제 Linux baseline과 해당 repository의 승인 artifact가 준비된 뒤 위 세 입력으로 workflow를 수동 실행하고 실제 로그/환경/실패 evidence를 006 기록에 남긴다.
