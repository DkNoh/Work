# 009 — 복잡 조회와 서버 정렬·페이지·가상 표

상태: **구현·로컬 통합 검증 완료**. 008의 구현·문서·로컬 통합 검증을 마친 뒤 착수했다. 모바일 compact 레이아웃을 포함한 최종 `scripts/build.sh`는 종료 0이며 서버 87개 검사 안에 신규 보고서 10개 검사가 포함된다. 새 JAR의 기존 41개·보고서 5개 E2E, 전체 DOM axe 61회, 보고서 12장 실제 이미지 검토와 별도 시각 비교 4개도 통과했다. 010~012는 코드 착수 전 대기다. Redis/JWT/SSO 제외, JDK21/H2·세션/CSRF·공통 `sc` UI·기존 요구사항 URL/JSON/권한/revision 계약을 유지한다.

단순 ID·쓰기와 권한·상태 전이·CAS·history/audit는 기존 Service가 소유한다. MyBatis는 같은 DataSource/JpaTransactionManager를 사용한다. 보고서 통계와 페이지의 동시 변경 일관성은 앱의 읽기 전용 SERIALIZABLE 경계와 실제 두 연결 검사로 확인한다. H2의 READ_COMMITTED/REPEATABLE_READ에서는 phantom이 가능하며, SERIALIZABLE의 동시 쓰기 직렬 동등성에도 제한이 있으므로 이 읽기 보고의 snapshot 검증을 전체 업무 쓰기의 보장으로 확대하지 않는다. 기존 외부 transaction 안의 REQUIRED 호출은 그 transaction의 isolation을 승계하는 경계를 기록한다. [H2 isolation](https://h2database.com/html/advanced.html#transaction_isolation). 프런트가 같은 자료를 Pinia/로컬 배열로 복제하거나 이전 페이지를 새 offset으로 표시하지 않는다.

ScTable의 asc→desc→정렬 해제 3상태를 유지한다. URL sort가 없으면 sorting props는 null이고 API 기본 정렬을 사용하며 화면에 이를 안내한다. 정렬·필터 변경은 page0, 정렬 해제는 URL sort/direction을 삭제한다. 파일/import `ScDataTable`, `ScVirtualTable`, 템플릿 `<sc-data-table>`, `<sc-virtual-table>`로 사용한다.

## 실제 서버와 공개 API

구현 파일은 Reference 앱의 `reference/reports/RequirementReportDtos.java`, `RequirementReportRows.java`, `RequirementReportSqlMapper.java`, `RequirementReportService.java`, `RequirementReportController.java`, `RequirementReportOpenApiConfiguration.java`와 `resources/dev/scframework/reference/reports/RequirementReportSqlMapper.xml`이다. 기존 `requirements/RequirementService.java`의 목록만 이름 batch 조회로 개선했다. 본문 저장·작성자 권한·상태 전이·revision/CAS·history/audit 경로는 유지한다. 테스트는 [RequirementReportIntegrationTest.java](../../backend/reference-app/src/test/java/dev/scframework/reference/reports/RequirementReportIntegrationTest.java)에 있다.

새 업무 API는 `GET /api/reports/requirements`, OpenAPI `operationId=requirementReport`다. 인증된 현재 DB actor를 사용하고 HTTP 200에 `{items,total,page,size,stats}`를 직접 반환한다. `RequirementReportPage`의 5필드는 모두 required다. 추가 success/data 봉투나 조회 성공 audit 쓰기는 만들지 않는다.

| Query 파라미터    | 실제 타입·기본값           | 경계와 의미                                                                   |
| ----------------- | -------------------------- | ----------------------------------------------------------------------------- |
| `q`               | string, 기본 `""`          | 최대 200자, 제목 부분 문자열. 공백 보존, `%`·`_`·역슬래시 literal 검색        |
| `menuId`          | 선택 integer/int64         | 해당 메뉴, 보관 메뉴의 기존 요청도 조회 가능                                  |
| `status`          | string, 기본 `""`          | 빈 값이면 전체, 지정하면 정확히 일치. 기존 목록처럼 알 수 없는 상태는 빈 결과 |
| `authorId`        | 선택 integer/int64         | 작성자 조건. 지정하더라도 타인 초안 공개 범위를 넓히지 않음                   |
| `screenVersionId` | 선택 integer/int64         | 해당 버전 조건. 009의 일반 요청은 null이므로 지정한 버전 결과는 비어 있음     |
| `page`            | integer/int32, 기본 **0**  | 0~1,000,000, 0부터 시작                                                       |
| `size`            | integer/int32, 기본 **20** | 1~100                                                                         |
| `sort`            | 선택 string enum           | `updatedAt/title/commentCount/historyCount/lastCommentAt`만 허용              |
| `direction`       | 선택 string enum           | `asc/desc`만 허용. sort만 있으면 desc, direction만 있으면 400                 |

sort/direction 모두 생략하면 `updatedAt DESC,id DESC`다. 모든 정렬의 동률은 id DESC이며 lastCommentAt은 asc/desc 모두 null을 마지막에 둔다. 행 건수·최종 댓글 정렬도 전체 필터 결과를 집계한 다음 페이지를 자르므로 현재 페이지만 먼저 정렬하는 동작과 다르다. 조회 범위·잘못된 정렬은 400/`INVALID_INPUT`이다. SQL 값은 `#{...}`로 바인딩하고 정렬 열·방향은 고정 `choose`만 사용한다.

`RequirementReportItem`의 **16필드는 모두 required**다. nullable 필드도 응답에서 생략하지 않고 null로 반환한다.

| 필드                              | 실제 JSON 타입                                                          |
| --------------------------------- | ----------------------------------------------------------------------- |
| `id`, `menuId`, `authorId`        | integer/int64                                                           |
| `menuName`, `title`, `authorName` | string                                                                  |
| `status`                          | `DRAFT/REQUESTED/NEEDS_INFO/REVIEWING/AGREED/ADO_LINKED` string         |
| `revision`                        | integer/int32, 최소 1                                                   |
| `assignedReviewerId`              | integer/int64 또는 null                                                 |
| `assignedReviewerName`            | string 또는 null                                                        |
| `createdAt`, `updatedAt`          | ISO UTC string/date-time                                                |
| `reviewDecision`                  | `UNREVIEWED/POSSIBLE/CONDITIONAL/MORE_INFO/IMPOSSIBLE` string 또는 null |
| `commentCount`, `historyCount`    | 0 이상 integer/int64                                                    |
| `lastCommentAt`                   | ISO UTC string/date-time 또는 null                                      |

`RequirementReportStats`의 **7키는 `DRAFT`, `REQUESTED`, `NEEDS_INFO`, `REVIEWING`, `AGREED`, `ADO_LINKED`, `unassigned`**이며 모두 required·0 이상 integer/int64다. 상태 6개 합은 total, `unassigned`는 `assigned_reviewer_id IS NULL`의 건수로 total 이하이다. page/size와 무관하게 같은 검색·현재 DB actor 공개 범위를 적용한 전체 결과다. 요청자 지정과 현재 검토 존재는 다르므로 미검토 건수를 unassigned로 계산하지 않는다.

Mapper의 `visibleRequirements` fragment를 두 SQL이 공유한다. 공개 범위를 먼저 적용하고 댓글 COUNT/MAX·이력 COUNT를 요청별로 집계한 뒤 1:1 현재 검토와 이름을 연결한다. 3댓글×4이력이 있어도 3/4이며 12/12가 아니다. CTE는 id/menu_id/title/status/revision/author_id/assigned_reviewer_id/created_at/updated_at **9개 메타데이터 열만** 읽는다. WHERE의 screen_version_id 조건은 원본 테이블에 유지했다. desired/reason/reference/followParts·이력 JSON·파일/업로드 경로·계정 hash는 보고서 응답에 노출하지 않는다.

## 합성 10k 측정과 EXPLAIN

최종 증거는 [performance-10000.json](../검증/009-performance-final/performance-10000.json), [bounded-queries.json](../검증/009-performance-final/bounded-queries.json), [explain-plans.json](../검증/009-performance-final/explain-plans.json)에 보존한다. `backend/reference-app/target/report-evidence`의 모바일 compact 최종 통합 테스트 결과 3개를 복사했다. 앞선 통합 두 번째 결과는 [009-performance-integration-second](../검증/009-performance-integration-second/performance-10000.json)에 원문 3개를 보존하여 덮어쓰지 않았다. 새 임시 in-memory H2에서만 10,000개의 합성 요청·댓글·이력을 만들었다. 실제 사용자 DB/업로드/secret·원본 자료는 사용하지 않았다.

환경은 JDK **21.0.11**, H2 **2.3.232**, 테스트 JVM의 in-memory H2·SERIALIZABLE 보고서 경계다. 자료 준비 153.410291ms, page 0→49→99를 size100으로 각 **한 번** 순차 관측했다. 측정용 별도 warmup이나 반복 분포/percentile은 없으며 그 전에 같은 JVM에서 소규모 보고서 테스트가 수행될 수 있다. elapsed는 두 SQL과 서비스 DTO 변환을 포함하고 HTTP/브라우저 왕복 시간은 포함하지 않는다.

| 전체 요청 | page / size | 반환 행 | MyBatis 실제 JDBC prepare | 최종 관측 시간 |
| --------- | ----------- | ------- | ------------------------- | -------------- |
| 10,000    | 0 / 100     | 100     | 2                         | 56.211792ms    |
| 10,000    | 49 / 100    | 100     | 2                         | 30.083834ms    |
| 10,000    | 99 / 100    | 100     | 2                         | 29.047042ms    |

첫/중간/마지막 ID와 순서·total·자식 건수를 실제 SQL 기준으로 비교했고 타인 DRAFT 필터와 literal 검색도 확인했다. 개발 기기의 단일 관측값은 운영 SLA·성능 보장·최대 지연·부하 테스트 결과가 아니다.

기존 `/api/requirements`는 서로 다른 메뉴/작성자/담당자를 가진 1행·100행에서 현재 actor 조회 1 + Querydsl count/page 2 + 메뉴 batch 1 + 계정 batch 1 = **5/5개의 Hibernate prepare**를 확인했다. 빈 결과는 이름 batch를 생략하여 **3개**다. 보고서의 **2개**는 앱과 DB 사이 roundtrip/prepare 횟수이며 물리 작업량이 자료량에 무관한 상수라는 의미가 아니다.

EXPLAIN ANALYZE는 생산 MappedStatement의 실제 BoundSql과 같은 DefaultParameterHandler 바인딩으로 실행했다. menu 필터는 H2의 FK `CONSTRAINT_INDEX_C`, 부모/이름/현재 검토 조인은 PK, 댓글/이력은 FK 인덱스 lookup이 계획에 나타난다. H2 optimizer는 선집계 subquery에 요청 ID 조건을 push down할 수 있어 내부 lookup·scan 작업이 있다. 기본 전체 결과 계획의 tableScan은 전체 필터 집계 특성이다. scanCount·원문 계획을 보존하며 모든 정렬의 index-only 수행이나 일정한 물리 비용을 주장하지 않는다. 이 측정에서 신규 index migration을 추가할 근거가 없어 기존 인덱스를 유지했다.
