# 012 메시지·파일 journal·백업/복원 계약

현재는 구현 및 실행 검증 중이다. 첫 main 컴파일과 운영 Reference profile startup, 실제 Rabbit/crash 테스트를 포함한 전체 서버 195개, 새 root 복구 7그룹이 통과했다. 프런트·관측·새 0.3 소비 앱을 포함한 최종 통합은 Root가 별도로 검증한다. Redis·JWT·SSO는 사용하지 않는다.

## 메시지와 앱 책임

공통 `ScMessage`는 opaque UUID, 등록 type, schemaVersion=1, UTC micro 시각과 최대 16KiB UTF-8 JSON payload를 받는다. `toString`에는 payload를 포함하지 않는다. codec은 알 수 없는 필드를 거절하고 Java 역직렬화·클래스 헤더를 사용하지 않는다. `MessageHandler`는 등록 type과 payload 검증, 동일 DB 트랜잭션의 effect를 소유한다.

| 경계            | 구현 계약                                                                                                                                                                                                 |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 업무 publish    | `DurableMessagePublisher.enqueue`는 실제 활성 트랜잭션을 요구한다. 업무 변경과 outbox INSERT가 같은 DataSource/JpaTM에 참여하여 함께 commit/rollback한다.                                                 |
| broker dispatch | DB claim은 `REQUIRES_NEW`, confirm 대기는 `NOT_SUPPORTED`, 결과 CAS는 `REQUIRES_NEW`다. persistent 메시지·correlated confirm·mandatory return을 확인한다. 최대 dispatch 시도는 5회다.                     |
| 소비            | 완료 inbox를 먼저 확인한다. inbox INSERT·handler effect·COMPLETED 변경이 같은 새 트랜잭션으로 commit된 뒤 동일 channel에 manual ACK한다. 실패하면 효과/inbox를 rollback한다.                              |
| 업무 재시도     | quorum 작업 큐 `x-delivery-limit=4`와 `basic.reject(requeue=true)`를 사용한다. 최초+재전달 최대 5회이며 DB `handler_attempts` 예약도 최대 5회로 제한한다. `basic.nack`로 failure count를 우회하지 않는다. |
| 중복            | 이미 완료된 inbox는 handler와 attempt 예약을 건너뛰고 ACK한다. 처리 중 동시 중복의 예약은 한도를 소모할 수 있으나 inbox PK가 중복 effect commit을 막는다.                                                 |
| DEAD            | terminal observer가 known envelope만 DEAD로 변경하고 ACK한다. COMPLETED는 DEAD로 바꾸지 않는다. ADMIN retry는 DEAD+미완료 조건 CAS이며 dispatch/handler attempt를 초기화한다.                             |
| DLQ DB 장애     | 업무 handler를 다시 실행하지 않고 terminal envelope를 보존한다. DLQ의 delivery-limit=-1과 bounded delayed retry는 DB 기록/ACK용 transport 재전달이며 업무 재시도 5회와 구분한다.                          |
| 안전한 관측     | `OperationalEventSink`의 등록 Kind/Outcome/opaque eventId만 기록한다. payload·경로·Throwable·자격 증명을 전달하지 않는다. sink 실패는 업무 결과를 바꾸지 않는다.                                          |

작업 큐는 quorum/persistent/durable, at-least-once dead-lettering 및 reject-publish overflow를 사용한다. publisher confirm은 broker 수신의 증거이며 handler 성공의 증거가 아니다. 큐의 at-least-once 전달과 DB inbox를 결합한다. 애플리케이션의 비트랜잭션 외부 API 부작용을 exactly-once로 보장하지 않는다.

Reference의 등록 type은 `SECURITY_AUDIT`, `FILE_DELETE`, `MESSAGE_DEMO`다. 감사 성공 outbox는 업무 TX에 참여하고 rollback된 성공 이벤트를 남기지 않는다. 로그인 등 TX 밖 이벤트와 실패 감사는 별도 TX로 enqueue하며 enqueue 장애는 기존 인증/오류 HTTP 결과를 바꾸지 않고 고정 operational counter로 드러낸다. 감사 sink 호출은 consumer의 inbox TX에 참여한다.

공통 스키마는 앱 Flyway가 선택한다. Reference는 `db/operations-migration/V6__operations_messages.sql`, Starter는 audit V1과 함께 `db/operations-migration/V2__operations_messages.sql`을 사용한다. 기존 V1~V5는 수정하지 않는다. Starter의 MESSAGE_DEMO는 중립 effect 한 건만 남기며 Reference 업무 class/table을 import하지 않는다.

## 운영 API

Reference는 현재 DB actor의 ADMIN 역할을 매 요청 확인하며 서버 세션·CSRF를 유지한다. 메시징 OFF면 controller와 앱 feature 요청을 활성화하지 않는다.

| HTTP                                            | 입력                                             | 결과/권한                                                                            |
| ----------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `GET /api/operations/messages`                  | page 0..1,000,000, size 1..100, 등록 type, state | ADMIN, `OperationMessagePage`의 items/total/page/size.                               |
| `POST /api/operations/messages/{eventId}/retry` | UUID, `{}` 또는 body 없음                        | ADMIN+CSRF, DEAD CAS 성공 202 `OperationMessageItem`; 없음 404, 부적합 상태 409.     |
| `POST /api/operations/messages/demo`            | `{}` 또는 body 없음                              | ADMIN+CSRF, 고정 MESSAGE_DEMO를 enqueue하고 202 반환. 임의 payload/실패 주입은 없다. |

Item에는 eventId/type/state/dispatchAttempts/nextAttemptAt/createdAt/publishedAt/completedAt/lastFailureCode만 있다. payload·파일 key·내부 경로·secret은 반환하지 않는다. state는 PENDING/CLAIMED/PUBLISHED/COMPLETED/DEAD다. Starter는 자체 DTO와 ADMIN 권한 검사로 동일 목록/retry/demo 운영 계약을 소비하며 Reference 업무 API·DTO를 import하지 않는다.

## 파일 journal과 삭제

`sc.framework.file-storage.durable-cleanup-enabled=true`이면 `LocalFileStorage`가 첫 쓰기 때 root의 저장소 잠금을 잡는다. opaque UUID별 `.pending/<key>`에 버전/runId/시각을 force하고 `.part/<key>`에 제한된 bytes를 쓴다. bytes를 force한 뒤 UUID 최종 파일로 atomic move한다. 파일·journal symlink와 비정상 entry는 거절한다. root 생성은 첫 실제 접근까지 지연한다.

업무 metadata commit 후 journal을 제거한다. commit 전 crash의 이전 run journal은 `FileReferenceLookup`으로 현재 DB 참조를 조회한다. 참조가 있으면 journal만 지우고, 없으면 FILE_DELETE outbox를 새 TX에 넣은 뒤 journal을 지운다. 중간 crash는 중복 삭제 메시지가 될 수 있으며 idempotent UUID 삭제와 inbox가 안전하게 처리한다. 현재 run의 미완료 파일은 startup recovery가 삭제하지 않는다.

metadata 삭제와 FILE_DELETE outbox는 같은 업무 TX다. rollback이면 둘 다 취소된다. 준비 실패/rollback cleanup의 enqueue 실패는 고정 counter와 남아 있는 journal로 드러낸다. 삭제 handler는 실행 시 다시 참조를 확인하여 연결된 원본 이미지를 삭제하지 않는다. 실제 IO 실패는 inbox/effect rollback과 유한 retry/DLQ로 전달된다.

Reference adapter는 `stored_file.storage_key`의 commit된 참조를 확인한다. Starter storage-demo는 현재 실행 whitelist만 인정하는 중립 예제다. Starter의 ephemeral 파일 참조가 재시작·백업에 보존되는 것으로 표현하지 않으며, 영속 metadata·이미지/PDF 복원은 Reference에서 검증한다.

이 journal은 프로세스 crash 경계를 대상으로 한다. 전원 장애·파일시스템 손상·네트워크 파일시스템의 atomic move/lock 동작은 별도의 환경 검증이 필요하다.

## runtime 잠금과 single-set 백업

`sc.framework.operations.enabled=true`, `runtime-root=<명시한 SC_HOME>`이면 Java `RuntimeMaintenanceLock`이 `.sc-runtime.lock`의 byte 0, length 1을 독점한다. DataSource와 FileStorage는 이 bean에 의존하므로 runtime lock을 먼저 확보하고 종료 순서에서도 lock보다 먼저 닫는다. Python은 같은 `fcntl.lockf(LOCK_EX|LOCK_NB,1,0)`를 사용한다. `flock`과 혼용하지 않는다.

```bash
python3 scripts/backup-runtime.py \
  --runtime-root /absolute/own-runtime \
  --jar /absolute/fresh-reference.jar \
  --output /absolute/new-backup

python3 scripts/restore-runtime.py \
  --backup /absolute/new-backup \
  --runtime-root /absolute/new-empty-runtime \
  --jar /absolute/same-reference.jar
```

백업은 정지된 단일 H2 `.mv.db`와 uploads UUID/`.pending`/`.part`를 하나의 private set으로 복사한다. 파일 size/SHA256, 실제 JAR SHA/Implementation-Version, 동일 JAR의 H2 runtime에서 읽은 Flyway SQL version/script/checksum을 manifest로 보존한다. IFEXISTS/read-only를 사용하며 schema 조회 후 source inventory 불변을 다시 확인한다. secret·로그·trace DB·lock 파일은 복제하지 않는다. 원본 WorkboardVue/workboard runtime은 입력으로 거절한다.

복원은 새 빈 root에서만 staging copy→hash/schema/build 검사→rename을 수행한다. 같은 JAR SHA만 허용하고 기존 실행 자료를 덮어쓰지 않는다. 세션은 복제하지 않으며 private 연결·bootstrap secret을 새 환경에 별도로 제공한다. backup이 포함하는 H2의 저장된 사용자 hash는 private data set의 일부이고 로그·manifest에 출력하지 않는다. COMPLETED/inbox는 그대로 보존한다. DEAD는 자동 재실행하지 않으며 ADMIN 명시 retry 경계를 유지한다.

현재 Python 백업과 NIO/lockf 상호 운용 검증은 POSIX 환경용이다. Windows native lock·실제 원격 CI·사용자 원본 자료 복구는 검증 대상에 포함하지 않는다.

## 설정과 등록 작업

| 설정                                                | 기본/제약                                                                             |
| --------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `sc.framework.messaging.enabled`                    | false, 활성 시 Boot RabbitTemplate/ConnectionFactory 및 동일 DS/JpaTM 사용.           |
| `application-id`                                    | 3..48 lower-case 등록 이름. 독립 테스트 runtime은 UUID suffix로 broker 큐를 격리한다. |
| `max-payload-bytes`                                 | 16,384 이하.                                                                          |
| `publish-max-attempts`                              | 기본 5, 1..5.                                                                         |
| `confirm-timeout` / `lease`                         | 5s/30s, lease는 confirm timeout보다 커야 한다.                                        |
| `poll-interval` / `batch-size` / `prefetch`         | 1s/20/10, bounded 설정.                                                               |
| `delivery-limit`                                    | 4 고정.                                                                               |
| `retry-min` / `retry-max`                           | 1s/30s, publish 재시도와 native failed-delivery 지연에 사용.                          |
| `retention-days`                                    | 30, 7..365, COMPLETED outbox/inbox만 정리.                                            |
| `sc.framework.audit.durable-enabled`                | false, messaging ON과 함께 선택.                                                      |
| `sc.framework.file-storage.durable-cleanup-enabled` | false, recoverable storage/앱 reference adapter 필요.                                 |
| `sc.framework.operations.enabled` / `runtime-root`  | false/명시 root, 활성 시 runtime maintenance lock 필수.                               |

Boot 설정 `spring.rabbitmq.publisher-confirm-type=correlated`, `publisher-returns=true`, `template.mandatory=true`를 필수 검사한다. OUTBOX_DISPATCH/FILE_RECOVERY 작업은 `NON_TRANSACTIONAL`이다. SAFE_RETENTION은 Tokens의 합성 등록 작업이 메시지·브라우저·완료 실행 이력을 같은 TX로 정리하며 실제 구현 job class/임의 payload를 HTTP에서 받지 않는다.

첫 전체 테스트의 [testCompile 실패](../검증/012-backend-tests-first.log)는 AssertJ와 generic execute의 overload 모호성을 명시 타입 인자로 수정했다. 두 번째 전체 Maven은 Root 관측 fixture의 macOS tmp symlink 2error로 실패했으므로 담당 13개 PASS와 전체 빌드 성공을 구분한다. Root는 canonical fixture로 수정했다. 추가 `MessageCrashBoundaryTest`는 실제 confirm 뒤 DB mark 전 및 handler commit 뒤 ACK 전에서 test-only JDBC/channel proxy barrier와 자기 child JVM SIGKILL을 사용하며, 제품 debug hook을 추가하지 않았다. 이 두 추가 테스트를 포함한 fourth 전체 195개 PASS가 현재 서버 근거다. Root가 추가한 관측 회귀 1개를 포함할 다음 실행 결과는 아직 미확인이다.

복구 [first](../검증/012-runtime-recovery-first.json)/[second](../검증/012-runtime-recovery-second.json)는 앞의 6그룹이 통과하고 마지막 삭제가 실패했다. 검증용 custom requester login 뒤 pre-login CSRF를 재사용한 helper가 원인이었다. post-login CSRF를 다시 받아 third 7/7그룹을 통과했으며 제품 파일저장 코드를 바꾸지 않았다. 실제 JAR는 실행 시작에 자기 private fixture로 SHA 검증 복사하여 Root의 후속 빌드와 겹쳐도 실행 중 바뀌지 않게 고정했다. 임시 H2/secret/uploads/child 자료는 정리됐고 원본 runtime을 사용하지 않았다. 이 보고서의 crash는 실제 storage adapter의 partial-write child를 대상으로 하며 메시지 confirm/ACK crash는 별도 JUnit 근거로 구분한다.

실패 증거는 초기 로그와 함께 보존한다. source 작성만으로 체크하지 않는다. Root가 실제 Maven/JAR/broker/백업 CLI를 순서대로 실행한다.
