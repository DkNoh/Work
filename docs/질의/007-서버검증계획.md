# 007 요구사항 서버 검증 계획

이 문서는 [007 계약 조사](007-요구사항계약조사.md)·[007 서버 설계](007-서버설계.md)와 기존 서버 테스트 소스를 바탕으로 작성한 **미실행 검증 계획**이다. 테스트 코드·업무 서버·프런트는 이 작업에서 변경하지 않았다. 006 검증을 마친 뒤 007 구현과 함께 아래 테스트를 작성하고 실제 결과를 남긴다. 표의 기대 결과를 실행 통과 기록으로 해석하지 않는다.

WorkboardVue는 문서/소스만 읽는다. 원본 DB·업로드·비밀번호·`.runtime`은 접근하거나 복사하지 않는다. 신규 테스트는 별도 임시 H2·합성 사용자·600 권한의 임시 secret·별도 포트만 사용하고 모두 종료/정리한다. Redis·JWT·SSO 제외를 유지한다.

## 테스트 fixture와 파일 책임 제안

각 테스트가 필요로 하는 자료를 명시적으로 준비한다. 하나의 거대한 base test가 모든 사용자·메뉴·요청을 숨겨서 만들지 않는다. 아래 이름은 생성 제안이며 현재 파일이라고 주장하지 않는다.

SecurityMockMvc의 `with(user(...))`만으로 인증 테스트를 끝내지 않는다. 정식 로그인·DB 계정·CSRF·logout은 실제 필터로 검사한다. 순수 권한 조합에 mock authentication을 쓰면 DB actor resolution까지 검증했는지 구분하고, 역할별 핵심 흐름은 실제 로그인으로 반복한다.

테스트 메서드를 자동 rollback transaction으로 감싸면 commit/AFTER_COMMIT/audit와 HTTP 요청의 실제 transaction 경계가 가려질 수 있다. 원자성·감사·동시성 테스트는 외부 test transaction을 사용하지 않고 Service/TransactionTemplate/EntityManager의 실제 commit/rollback을 검사한다. 필요 rollback은 테스트에서 명시적으로 유발하고 이후 **새 transaction**에서 결과를 확인한다.

BOOT-02/03에서 secret 파일 자체를 반드시 요구할지는 [서버 설계](007-서버설계.md)의 초기 bootstrap 정책에 맞춰 구현 시 고정한다. 검증 목적은 기존 DB 계정의 자동 재설정을 막는 것이다. 원본 계정·hash를 복사하여 확인하지 않는다. bootstrap 최소16 UTF-8바이트와 `/users` 최소12자 규칙을 하나로 합치지 않는다.

username에도 별도 경계가 있다. 현재 `SecretFileUsers`는 `[A-Za-z0-9._-]{1,64}`, 원본 사용자 생성 API는 같은 문자 종류의 3..60자를 허용한다. DB username 최대64자로 bootstrap과 호환시키고, `/users` Service에서는 원본 3..60자 규칙을 유지하는 설계가 가능하다. bootstrap의 1·2·60·61·64자와 API의 2·3·60·61자를 각각 검사한다. SQL 컬럼60자로 bootstrap64자를 잘라 저장하거나, API 상한을64로 임의 확대하지 않는다.

Reference frontend session decoder는 id/username/displayName/role 응답을 검증한 뒤 하나의 세션 객체로 연결하고 역할에서 roles를 계산한다. Starter 기본 decoder는 username/roles를 유지한다. 잘못된 형태를 TypeScript cast만으로 인정하지 않는 runtime 단위 검사, 이전 session generation 응답폐기, list/detail form의 author/assigned reviewer 비교·DB ID 표시까지 업무 E2E로 확인한다. 서버 me key assertion과 프런트 정규화 객체 key를 혼동하지 않는다.

## 동시 revision/CAS 검증 절차

CAS는 클라이언트 revision 비교만의 이름이 아니다. 실제 DB `UPDATE ... WHERE id=? AND revision=?`가 한 경쟁자만 저장하도록 보호하는지 검사한다. 수동 SQL 문자열 자체나 예외 클래스 이름만 확인하지 않고 최종 데이터/응답/이력을 확인한다.

| ID     | 재현                                                                        | 통과 기준                                                                                                      |
| ------ | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| CAS-01 | 같은요청/현재revision으로서로다른제목의실제동시HTTP PUT2개                  | 한개200·한개409/REVISION_CONFLICT, revision은정확히+1·승자제목만저장·성공EDIT history1개                       |
| CAS-02 | 별도EntityManager/transaction2개가revision r을먼저읽음→첫commit→두번째flush | 두번째실제@Version충돌·loser본문/관계/history미저장. 먼저읽은managedEntity에대한검사로client비교뒤경쟁방어증명 |
| CAS-03 | reviewupsert/본문쓰기·담당자변경이동시에같은revision사용                    | 최종담당자/currentreview상호모순없음·loser관계rollback·성공명령별history와응답일치                             |
| CAS-04 | 고정Clock/같은updatedAt에서반복review또는같은상태본문쓰기                   | 각유효변경revision이한번씩증가·historyafter와응답일치. timestamp변경에만dirtycheck를의존하지않음               |
| CAS-05 | 같은담당자no-op·댓글을정상변경과비교                                        | no-op/comment가revision/updatedAt를증가시키지않음. stale no-op입력은409                                        |

CAS-02는 첫번째와 두번째 읽기를 CountDownLatch/barrier로 맞추고, 첫 commit이 끝난 뒤 두번째 flush를 허용한다. 두 transaction은 같은 실제 H2 DataSource의 서로 다른 connection/EntityManager를 사용한다. `Thread.sleep`으로 경쟁 확률을 만들거나 repository를 mock하여 낙관잠금 예외를 던지지 않는다. executor/future/latch 대기는 명시적 timeout·finally 종료·예외 전파를 둔다. H2 lock timeout이 나면 그것을 revision409 성공으로 위장하지 않고 재현 구조/실패 근거를 기록한다.

CAS-01의 단순 동시 시작은 두번째 요청이 첫 commit 이후에 읽어도 client revision에서409가 될 수 있다. 따라서 실제 version 비교 뒤 경쟁을 증명하는 CAS-02를 별도로 실행한다. CAS-02의 detached merge만으로 HTTP409 serialization과Service관계rollback이 보장된다고 보지도 않는다. 두 계층이 서로 다른 실패를 확인한다.

동시성 테스트는 Spring test class의 외부 transaction을 사용하지 않는다. worker thread는 SecurityContext가 자동 전파된다고 가정하지 않고 명시적 실제 session/actor를 전달한다. 보안 문맥의 threadlocal이 이전 테스트로 새지 않는지 종료 후 확인한다.

민감값 검사에서는 테스트가 만든 임시 canary만 사용한다. 실제 개발 비밀번호/로그를 탐색하지 않는다. 실패 로그는 무엇이 유출됐는지 값을 출력하지 않고 경계·필드명·유출 유무를 보고한다. 축약된 audit event 한 개만 검사하고 전체 저장행/예외 경로의 민감값 제외를 완료했다고 기록하지 않는다.

현재 [check-openapi.py](../../scripts/check-openapi.py)는 Reference JAR과 단일snapshot을 기본으로 사용한다. 007에서 Reference me가확장되므로 기존ReferenceIntegrationTest의SessionResponse metadata assertion을의도한확장계약에맞춰갱신하고Starter의기본계약검사를추가한다. snapshot의형식/명칭을바꾸는작업은root와조율하며, 서버별snapshot·frontend생성타입·업무schema수동검증을혼동하지않는다.

## 실행 순서·완료 조건과 후속 범위

아래는 **향후 실행 순서**다. 아직 실행 명령/성공 로그를 이 문서에 붙이지 않았다.

1. public session 확장과 DB 사용자/bootstrap을 구현하고 auto-config/기존예제/Starter 인증 회귀부터 실행한다. 중복mapping·빈후보·잘못된UserDTO가 남으면 업무UI로 진행하지 않는다.
2. 앱 V2/V3 migration·JPA Entity validate·입력/조회/권한/상태/comment/history HTTP 테스트를 실행한다. 테스트 fixture는 실제 source JSON/정식 API를 사용한다.
3. 실제 동시 transaction/HTTP CAS·고정Clock revision·주업무/관계/history rollback과audit독립저장을 검증한다. 실패/lock timeout은 별도 기록한다.
4. 실제 devJAR OpenAPI/snapshot/생성타입·정식 DB로그인+일반요구사항 E2E를 실행한다. direct `/workspace`·`/requests/{id}` 새로고침과list/detail form 입력원본·역할전환·400403409500·late응답·logout을 포함한다.
5. 006 accessibility·시각회귀와기존001~005 기능을 다시확인한다. 원본source보호검사·새임시자료정리·버전/라이선스·문서링크를 확인하고 그 실제 결과로만007 완료를 표시한다.
