# 007 요구사항 서버 도입 설계

이 문서는 2026-10-06의 [요구사항 계약 조사](007-요구사항계약조사.md)와 현재 ScFramework 서버 소스를 바탕으로 작성한 **구현 준비안**이다. 005 검증 결과를 007 완료로 바꾸지 않으며, 006의 실제 JAR 접근성·회귀 검증을 마친 다음 007을 구현한다. 여기에서 제안한 파일·빈·속성·DTO는 아직 구현되었다는 뜻이 아니다. 이 작업에서는 문서만 작성하고 원본 DB·업로드·비밀번호·`.runtime`을 읽거나 복사하지 않았다.

기준은 Spring Boot 3.5.16·JDK 21·H2·세션/CSRF다. Redis·JWT·SSO 제외를 유지한다. 원본 URL·JSON·작성자/담당자 권한·상태 전이·revision을 보존하고, 새 기능은 기존 `/examples`·`/patterns`와 다른 업무 경계에 추가한다. [전체 조건부 범위](조건부기술-전체구현.md)의 Day.js와 H2 보안 감사도 007에서 구현·검증한다.

## 구현 순서와 모듈 책임

| ---- | ----------------------------------------------------- | ---------------------------------------------------------------------------------- |

007의 업무 패키지 제안은 `backend/reference-app/src/main/java/dev/scframework/reference/identity`, `menu`, `requirements`다. Entity/Repository/Service/DTO/Controller는 각각의 업무 안에 둔다. 기존 중립 `example` 모델에 요구사항 필드를 붙이지 않고, 공통 모듈이 Reference의 Entity·User DTO·업무 enum을 import하지 않는다. Controller는 JSON/입력·인증 문맥 전달, Service는 권한/상태/revision/트랜잭션, Repository는 저장·조회, DTO 변환은 응답 조립을 맡는다.

008에서 MapStruct·Lombok과 Jakarta Querydsl APT의 JDK 21 호환성을 실제 검증한 다음 도입한다. 007은 명시적인 생성자/메서드와 작은 수동 DTO mapper를 사용한다. 008/009의 복잡 MyBatis join·집계·count/성능 작업을 미리 구현 완료로 표시하지 않는다. 이미 있는 MyBatis 중립 summary와 OpenFeign loopback 예제는 유지한다.

| ------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |

`spring.main.allow-bean-definition-overriding=true`를 해결책으로 쓰지 않는다. 공통 auto-configuration은 소비 앱 일반 설정이 처리된 뒤의 빈 조건으로 backoff하고, 넓은 component scan으로 업무 빈을 찾지 않는다. Bean 메서드에는 구체 타입을 노출하여 조건 판단을 돕는다. [Boot 3.5 공식 auto-configuration 기준](https://docs.spring.io/spring-boot/3.5/reference/features/developing-auto-configuration.html).

### me 경로·DTO·인증 SPI 제안

현재 원본 [Api.me](../../../WorkboardVue/backend/src/main/java/kr/co/screenreq/Api.java:50)는 `id,username,displayName,role`만 반환한다. 신규 기본 me는 `username,roles[]`다. Reference의 me에 새 봉투나 임의 `roles` 필드를 추가하여 원본 User 응답을 대체하지 않는다.

1. 공통 `CommonEndpoints`에는 health·CSRF만 남긴다. `DefaultSessionEndpoints`가 기본 `/api/auth/me`와 중립 `SessionResponse(username,roles)`를 소유하도록 분리한다.
2. 기본 session 빈에는 `sc.framework.session-endpoint.enabled=true` 기본값과 `@ConditionalOnProperty(..., havingValue="true", matchIfMissing=true)`를 사용한다. 소비 기본 endpoint 재정의에는 구체 타입/빈 조건도 둔다. 이 속성은 me endpoint만 비활성화하며 로그인·CSRF·인증 필터를 끄지 않는다.
3. Reference는 속성을 false로 두고 `ReferenceSessionController` 하나가 `UserResponse`를 반환한다. Starter는 기본값 true와 기존 me를 유지한다. `RequestMappingHandlerMapping`으로 각 앱의 `/auth/me`가 정확히 하나인지 검사한다. 별도 subclass에서 기본 me 반환 타입을 억지로 바꾸지 않는다.
4. 로컬 인증 provider SPI는 Spring Security의 기존 `UserDetailsService`와 `PasswordEncoder`다. Reference `DatabaseUsers`는 username으로 H2의 사용자/BCrypt hash/role을 조회한다. 권한은 `ROLE_REQUESTER/ROLE_REVIEWER/ROLE_ADMIN`이며 비밀번호·hash는 공개 DTO에 포함하지 않는다. 외부 SSO/JWT provider는 만들지 않는다. [공식 UserDetailsService 경계](https://docs.spring.io/spring-security/reference/6.5/servlet/authentication/passwords/user-details-service.html).
5. 앱 `ActorResolver`는 인증된 username을 DB 사용자로 다시 확인하고 `Actor(id,username,displayName,role)`를 만든다. 인증 객체가 단순 username/authority를 담아도 숫자 author/reviewer는 DB를 원본으로 결정한다. anonymous 인증을 actor로 인정하지 않으며 클라이언트 authorId/role을 신뢰하지 않는다. 업무 권한은 현재 DB role을 확인한다. 기존 세션 authority의 ADMIN 표시만으로 타인 쓰기를 허용하지 않는다.

공통 [runtime Identity](../../frontend/packages/runtime/src/runtime.ts:13)는 지금 응답을 타입 단언하여 `username/roles[]`로 저장한다. Reference me 변경과 함께 **응답 해석 확장점**을 구현해야 한다. 제안은 기본 동작을 보존하는 `decodeIdentity(payload: unknown)` 옵션과 앱별 확장 Identity 타입이다. Reference adapter는 생성된 `UserResponse`의 런타임 형식을 확인하고, id/displayName/role을 가진 한 세션 객체에 role에서 계산한 roles를 연결한다. Starter는 기존 응답 해석을 사용한다. 별도 Pinia 사용자 복사본·별도 Axios·두 번째 `/me` 컨트롤러를 만들지 않는다. 디코딩 실패를 인증 성공으로 취급하지 않으며 세션 generation 검사/Query 초기화/이전 응답 폐기를 그대로 유지한다. 이 generic 타입/주입의 구체 API는 007 구현 시작 시 공개 계약과 소비 타입 테스트로 고정한다.

### bootstrap과 합성 계정

[SecretFileUsers](../../backend/framework-autoconfigure/src/main/java/dev/scframework/autoconfigure/security/SecretFileUsers.java)는 새 secret 파일의 존재·600 권한·16..72 UTF-8 바이트·username을 검사하고 메모리 ADMIN 하나를 만든다. Reference DB 인증이 이 메모리 저장소를 동시에 사용해서는 안 된다.

| 항목            | Reference DB 전환 정책                                                                                                                                         |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 초기 관리자     | Flyway 후 앱 소유 bootstrap Service가 **빈 사용자 저장소일 때만** 새 secret 파일을 읽어 hash와 ADMIN을 저장. 원본 계정/해시를 이관하지 않음                    |
| 재기동          | 기존 계정을 다시 생성하거나 파일 비밀번호로 DB hash를 덮지 않음. 기존 사용자 수/ID/업무 FK 유지                                                                |
| 기동 순서       | migration·bootstrap 완료 뒤 실제 로그인 사용 가능. readiness를 bootstrap 전에 UP로 판단하지 않도록 기동 검사 추가                                              |
| 파일 처리       | 공통 secret 검증 정책을 재사용할 때 읽기/검증을 별도 helper로 정리. helper가 원문을 로그·예외·응답으로 내보내지 않음. 테스트에도 새 임시 파일만 사용           |
| 사용자 생성 API | 원본 `POST /api/users` ADMIN·200. username `[A-Za-z0-9_.-]{3,60}`, displayName nonblank/max80, role 세 값. password는 최소12자·UTF-8 최대72바이트; hash만 저장 |
| 규칙 차이       | bootstrap의 최소16 UTF-8 바이트와 일반 사용자 password의 최소12자 계약은 서로 다름. 하나로 합쳐 API 규칙을 바꾸지 않음                                         |
| 검증 자료       | 임시 H2의 작성자 A·지정 REVIEWER B·미지정 REVIEWER C·ADMIN D. 임의 기본 비밀번호·원본 username/비밀번호·실행 DB 재사용 없음                                    |

SQL migration에 비밀번호/BCrypt hash를 하드코딩하지 않는다. 사용자·메뉴는 실제 API 또는 테스트 fixture Service로 준비한다. 동시 bootstrap은 DB username unique 제약을 활용하고 정상 신규 최초 등록과 중복 오류를 구분한다. 사용자 관리 UI/비밀번호 변경·session 연장 UI는 010 범위이며, 새 계정 API/인증 기반은 007에 필요하다.

## H2 Entity와 migration

현재 신규 [V1__example_baseline.sql](../../backend/reference-app/src/main/resources/db/migration/V1__example_baseline.sql)은 수정하지 않는다. 기존 ScFramework의 V1 H2에 적용 가능한 후속 앱 migration을 작성한다. 원본 SQLite `schema_version/AUTOINCREMENT/strftime/PRAGMA`와 실행 자료는 가져오지 않는다. `ddl-auto:validate`, `open-in-view:false`, 단일 DataSource와 JpaTransactionManager를 유지한다.

| migration 제안                  | 테이블/제약                                                                                                                  | Entity·007 소유                                                                          |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `V2__requirements_baseline.sql` | `app_user`: BIGINT identity PK, username UNIQUE, display_name, password_hash, role CHECK, created_at                         | `identity/UserEntity`, `UserRepository`; hash 없는 UserResponse                          |
| 같은 V2                         | `menu`: BIGINT identity PK, nullable self parent FK, name, sort_order, active INTEGER CHECK 0/1, parent/sort 인덱스          | `menu/MenuEntity`, `MenuRepository`; 보관 메뉴도 목록 반환                               |
| 같은 V2                         | `requirement`: 업무 본문·menu/author/assigned_reviewer FK·status CHECK·similar INTEGER CHECK·revision>=1·시각                | `requirements/RequirementEntity`, `RequirementRepository`; `@Version Integer revision=1` |
| 같은 V2                         | `review`: requirement_id PK/FK, 판단/사유/조건/범위/제외/완료기준/규모·reviewer FK·시각                                      | 요청당 현재 검토 하나. 원본처럼 필요 시 upsert/담당자 변경 시 삭제                       |
| 같은 V2                         | `comment`: identity PK, requirement/author FK, body, created_at, request/id 인덱스                                           | ID 오름차순. 요청 revision을 변경하지 않음                                               |
| 같은 V2                         | `change_history`: identity PK, requirement/actor FK, action, before_json nullable, after_json, created_at, request/id 인덱스 | ID 내림차순. 본 변경과 같은 트랜잭션                                                     |
| `V3__security_audit.sql`        | `security_audit_event`: identity PK, actor 식별·time/action/outcome/resource/requestId/reasonCode, 조회 인덱스               | 공통 audit adapter가 사용하되 DDL/Flyway 활성은 소비 앱이 소유                           |
| 010 후속 migration              | `screen/stored_file/screen_version/annotation/attachment/ado_link`와 FK/unique/좌표 제약                                     | 실제 파일/이미지/ADO API가 구현되는 단계에 추가                                          |

Java Entity는 명시적 getter/변경 메서드와 protected 기본 생성자를 사용한다. 외부에서 모든 필드를 바꾸는 setter나 `@Data`를 기본으로 넣지 않는다. 관계는 원본처럼 숫자 ID를 매핑하고 FK는 migration이 보장하는 방식을 우선 사용한다. JSON 직렬화에 Entity나 지연 로딩 proxy를 직접 반환하지 않는다. 조회 DTO 조립은 트랜잭션 안에서 마친다.

본문 길이는 title200·desired20,000·reason/referenceText/followParts10,000을 DB/DTO에서 일치시키고, Review/Comment 길이도 각10,000으로 선언한다. 긴 history JSON은 CLOB 등 길이 제한이 충분한 타입을 사용한다. menu active·requirement similar는 응답에서 **정수0/1**이며 Entity의 내부 boolean 여부와 관계없이 DTO 변환으로 보존한다. role/status/decision/estimate는 문자열 enum 값으로 저장하고 ordinal을 쓰지 않는다.

007 일반 요청에서는 `screenVersionId`가 항상 null이어야 한다. 제안한 V2는 nullable scalar 컬럼과 명시적 `CHECK(screen_version_id IS NULL)`을 둘 수 있고, 입력 Service는 화면 버전/박스 값을 400으로 거절하여 미구현 기능을 저장하지 않는다. 010에서 실제 화면 테이블 생성→check 제거→FK 추가 순서의 migration으로 확대한다. 일반 요청 상세의 `annotation,screenVersion,ado`는 null, `attachments`는 빈 배열로 실제 JSON을 유지한다. 이 단계에서 빈 화면/파일 API를 성공 반환하는 가짜 구현은 하지 않는다. 기존 image/box 전체 계약은 [007 조사](007-요구사항계약조사.md)의 010 경계에 남긴다.

007 목록에는 menu/status/author/updated_at·assigned reviewer·screenVersion 단일 조건 인덱스를 준비하되 009에서 합성 규모/H2 실행 계획을 확인하기 전 성능 완료를 주장하지 않는다. sort는 updatedAt DESC,id DESC로 고정한다. 본문 내용의 검색·임의 정렬을 새 API 인자로 추가하지 않는다.

### UTC 저장과 날짜 표시 경계

원본 [WorkService.base](../../../WorkboardVue/backend/src/main/java/kr/co/screenreq/WorkService.java:83)는 `Instant.now().toString()`을 사용한다. 신규 Entity의 시각은 `Instant`와 H2 `TIMESTAMP WITH TIME ZONE`을 우선 검토하고, JSON은 UTC ISO 문자열로 직렬화한다. 실제 Hibernate/H2의 소수초 정밀도와 validate를 테스트해 고정해야 한다. 원본 Java Instant의 나노초를 Day.js의 밀리초 값으로 바꿔 다시 저장하거나 history snapshot의 시각을 임의 재작성하지 않는다. 시각 비교·revision 증가를 작은 Clock 간격에 의존하지 않도록 아래 revision 검사를 수행한다.

007 요구사항 입력에는 사용자 편집 날짜 필드가 없다. `createdAt/updatedAt`은 서버 전용이고 unknown JSON 필드로 거절한다. 임의 날짜 입력 API나 kanban dueDate를 요구사항 DTO에 추가하지 않는다. Day.js는 API 시각 **표시**와 날짜 값 검증 utility/예제·테스트에 실제 사용한다.

| 값 종류     | API/서버 원본                      | Day.js 사용·검증                                                                                                                 |
| ----------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 이벤트 시각 | UTC ISO 문자열, 서버 Clock/Instant | utc plugin으로 해석 후 명시한 표시 시간대와 ko/en locale로 표시. 없는 zone 문자열·overflow·잘못된 값을 성공 날짜로 표시하지 않음 |
| 달력 날짜   | 010 `dueDate:YYYY-MM-DD\|null`     | customParseFormat strict 검증. timezone 이동/`toISOString().slice(0,10)`으로 날짜를 바꾸지 않음                                  |
| 화면 표시   | 저장 전 입력·원본 API 시각 그대로  | 언어/시간대 변경은 표시 computed만 변경. 폼 reset·조회값 재저장 없이 초안 유지                                                   |
| 범위/경계   | 유효 형식과 실제 날짜              | 윤년2/29·없는2/30·월0/13·빈/null·UTC 자정 전후·Asia/Seoul 날짜 이동을 검사. 필요 IANA zone은 timezone plugin으로 명시            |

[Day.js strict parsing](https://day.js.org/docs/en/parse/string-format)은 customParseFormat과 형식의 정확한 일치를 요구하고, [UTC plugin](https://day.js.org/docs/en/plugin/utc)은 UTC/local 모드를 구분한다. 설치 버전·정확한 plugin·OSS 고지는 007 설치 시 manifest/lock 기준으로 확정한다. 아직 도입했다고 기록하지 않는다.

`@Schema`에는 required/nullable·길이·enum·positive·0/1·page 범위를 실제대로 적고 operation에 200/400/401/403/404/409를 명시한다. `Authentication`·내부 actor/Entity/hash는 숨긴다. 원본 요구사항·사용자·메뉴 POST/변경은 **200**이며 Example 생성201/삭제204 패턴을 가져오지 않는다. 성공 봉투는 추가하지 않는다.

원본 목록 status 문자열과 menuId/authorId/screenVersionId는 Controller에서 enum/Positive 검증을 하지 않는다. 알 수 없는 status·없는/음수 filter ID는 일치하는 자료가 없어 빈 목록이 되는 동작을 보존할지 source 기준으로 검사한다. 이를 무조건400으로 바꾸거나 OpenAPI enum만 보고 서버가 거절한다고 기록하지 않는다. q max200, page0..1,000,000, size1..100/default20, `%/_/backslash` literal 이스케이프와 고정 정렬을 유지한다.

기존 [ScOpenApiAutoConfiguration](../../backend/framework-autoconfigure/src/main/java/dev/scframework/autoconfigure/ScOpenApiAutoConfiguration.java)은 앱 OpenAPI 빈이 있으면 기본 문서 전체가 backoff한다. Reference가 me DTO만 바꾸려고 새 OpenAPI 빈을 선언해 로그인/logout 수동 경로·세션 보안·CSRF 설명을 잃지 않도록 한다. 명시적 Controller 반환 타입에서 User schema를 추출하고 필요한 앱 customizer를 추가하는 방식을 우선 사용한다. dev-only Swagger 정책과 production 문서 차단은 유지한다.

Reference snapshot/생성 타입에 업무 DTO를 추가하더라도 runtime이 업무 타입을 소비하지 않게 한다. 앱 feature가 생성 계약을 import하고 공통 session adapter는 unknown 경계를 검증한다. Reference/Starter의 서로 다른 me 스키마를 한 API snapshot이 양쪽 모두를 정확히 표현한다고 주장하지 않는다. 격리된 각 앱의 live 명세에서 me·health·CSRF·로그인/logout을 따로 검사하고, 기본 계약과 Reference 확장 snapshot을 구분할 공개 산출물 위치를 007 구현 시 고정한다.

## JPA Service·권한·revision

업무 권한은 [원본 WorkService](../../../WorkboardVue/backend/src/main/java/kr/co/screenreq/WorkService.java:41)의 검사 순서와 관계 조건을 따른다. UI의 버튼 표시나 `hasRole('ADMIN')`만으로 작성자/담당자 검사를 대체하지 않는다.

| 동작        | Service가 확인할 것                                                                                     | 저장·응답                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| list/detail | 인증 actor. DRAFT는 작성자/ADMIN만; 지정 담당자도 타인 초안 조회 불가                                   | list와 count가 같은 가시성 predicate, summary/detail 구분                                    |
| create      | 활성 메뉴·similar true의 followParts·007 일반 요청만                                                    | DRAFT·revision1·CREATE history·상세200                                                       |
| update      | 작성자→revision→입력/메뉴 관계. version 불변                                                            | REVIEWING/AGREED/ADO_LINKED만 REQUESTED, 나머지는 유지. 현재 review는 보존·EDIT history      |
| submit      | 작성자·revision·DRAFT/NEEDS_INFO                                                                        | REQUESTED·SUBMIT history. 담당자 미지정이어도 허용                                           |

| review      | REVIEWER/ADMIN·조회·작성자 아님·현재 지정 담당자·revision·DRAFT 아님                                    | review upsert, needsInfo true NEEDS_INFO/false REVIEWING·REVIEW history                      |
| agree       | 작성자·revision·REVIEWING·현재담당자의 POSSIBLE/CONDITIONAL review·scope/exclusions/acceptance nonblank | AGREED·AGREE history                                                                         |
| comment     | 요청 조회 가능한 인증 actor·body 입력                                                                   | 댓글 추가·상세200. 요청 revision/updatedAt/history를 바꾸지 않음                             |

ADMIN은 타인 DRAFT 조회와 담당자 지정은 할 수 있지만 타인 본문 수정/제출/합의는 할 수 없다. 미지정 ADMIN의 검토도403이다. 원본 본인검토는400, 담당자 아님은403처럼 source의 상태와 검사 순서가 구분되므로 모든 거절을403으로 합치지 않는다. 상세 존재404와 DRAFT 접근403도 source대로 검사한다.

각 쓰기는 Service 외부 호출의 `@Transactional` 하나에 요구사항·검토 변경·스냅샷 이력을 묶는다. CRUD repository마다 새 트랜잭션을 강제로 만들지 않는다. JPA managed entity를 수정하고 명시적 flush 후 새 revision을 DTO/history에 사용한다. 요청 revision 비교 후 실제 DB 낙관 충돌까지409/REVISION_CONFLICT로 변환한다. 최초 persist는 revision1을 유지하고 save의 merge 판단에 따라0으로 바뀌지 않는지 검사한다.

검토만 수정하거나 같은 상태의 내용 변경이라도 요청 revision은 한 번 증가해야 한다. 반대로 같은 담당자 no-op와 댓글은 증가하지 않는다. `updatedAt=Clock.now()` 변경만으로 version 증가를 보장하지 않는다. 같은 시각의 명령에서도 증가하는지 테스트하고 필요하면 명시적 요청 변경/강제 version 증가 방법을 선택한다. force increment는 flush 이후 언제 적용되는지까지 검증해야 하므로 DTO에 수동 `revision+1`을 얹거나 @Version 값을 직접 조작하지 않는다.

history snapshot은 원본처럼 기본 요구사항 필드 + annotation/review/ado/attachments다. comments/history/screenVersion은 snapshot에 포함하지 않아 재귀/불필요 확장을 막는다. before는 변경 전, after는 실제 flush 후의 새 revision과 관련 자료를 포함한다. 생성 before null, 담당자 변경 before에 이전review·after에는 null을 남긴다. snapshot 직렬화/이력 insert 실패는 주 쓰기도 rollback한다.

### 007 조회와 008/009 혼합 경계

007의 ID/username 단순 조회·CRUD 쓰기는 JPA다. 목록은 JPA Specification으로 가시성+필터를 한 곳에 만들고 Page/count에 동일 적용한다. 필요한 menu/사용자 표시 이름은 중복 ID를 모아 batch 조회하여 DTO를 조립할 수 있다. Querydsl/MyBatis를 먼저 추가하지 않고도 불필요한 행별 N+1과 전체 사용자 load를 피한다. 최적화가 009의 실제 복잡 보고 조회를 대신하지는 않는다.

008에서 같은 DataSource/JpaTransactionManager의 MyBatis 연결·JPA flush 전후 읽기·rollback/Feign timeout/오류를 확대한다. 009에서 복잡 join·집계/report·권한 count와 성능을 MyBatis로 구현할 때 기존 외부 JSON과 가시성을 유지한다. 동일 업무 조회를 런타임에 JPA/MyBatis 양쪽으로 상시 호출하지 않는다. `local-cache-scope:STATEMENT`와 JPA flush 의미를 보존하고 DDL implicit commit을 DML rollback 보장과 혼동하지 않는다.

## 보안 감사 SPI·H2 adapter

업무 `change_history`는 성공한 요구사항 스냅샷이다. 로그인 실패·권한 거절·CSRF 거절은 여기에 들어가지 않으므로 별도의 범용 감사가 필요하다. 공통 API는 business Entity나 본문 JSON을 받지 않도록 한다.

| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `framework-core/audit/SecurityAuditEvent`                | immutable actorSubject/optional actorId·occurredAt·action·outcome·resourceType/optional resourceId·requestId·reasonCode. 비밀번호/세션/token/본문 없음 |

core event의 optional numeric actorId는 Reference가 DB actor에서 제공하고 Starter는 username subject로 충분하다. 알 수 없는 로그인 실패 계정을 FK app_user에 억지로 연결하지 않는다. 감사 테이블에는 requirement/app_user FK를 두지 않아 거절·삭제·미등록 계정도 보존한다. 실패한 입력 username은 길이/제어문자를 제한하여 안전한 식별 정보만 남기고 비밀번호나 요청 파라미터 묶음을 저장하지 않는다. resource/requestId/reasonCode도 허용 길이·값을 제한한다.

새 auto-config는 `@ConditionalOnMissingBean(SecurityAuditSink.class)`로 소비 sink가 있을 때 JDBC sink를 만들지 않는다. 활성 상태에 sink가 없는 경우 조용히 noop 성공으로 흘리지 않고 기동 실패로 알려야 한다. 별도 consumer bean과 defaults가 함께 생성되지 않는 ContextRunner 테스트를 둔다. app migrations의 table 존재/쓰기 권한도 실제 H2 기동/쓰기에서 확인한다. JDBC 의존성의 optional 여부·starter 전달은 기존 POM에 맞춰 007에서 고정한다.

| 이벤트                  | 수집 위치·트랜잭션                                                                                                      |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 로그인 성공/실패·logout | 공통 security의 기존 success/failure/logout handler에서 명시적으로 publish. formLogin204/실패401/CSRF계약을 바꾸지 않음 |
| 필터 단계403/CSRF·401   | 현재 entryPoint/accessDenied handler와 연결. Advice만으로 필터 실패를 수집했다고 기록하지 않음                          |

| 업무 변경 성공          | 쓰기 transaction에 이벤트를 등록하고 실제 AFTER_COMMIT 뒤 별도 저장. rollback된 명령을 SUCCESS로 남기지 않음            |
| 변경 이력               | 계속 주 쓰기와 같은 트랜잭션. 범용 audit의 독립 저장 때문에 history의 원자성을 약화하지 않음                            |

AFTER_COMMIT/AFTER_ROLLBACK 단계에서 repository 저장을 원래 트랜잭션에 단순 참여시키면 변경이 커밋되지 않을 수 있다. 감사 writer의 외부 프록시 `REQUIRES_NEW` 등 **새 트랜잭션**을 명시하고 직접 호출/self-invocation으로 우회하지 않는다. 로그인처럼 트랜잭션이 없는 이벤트도 저장되도록 별도 nontransaction 경로 또는 명시적 fallback 정책을 둔다. 같은 이벤트를 security handler와 listener 양쪽에서 두 번 저장하지 않는다. [Spring 6.2 transaction event 의미](https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/event.html), [완료 후 데이터 접근 주의](https://docs.spring.io/spring-framework/docs/6.2.19/javadoc-api/org/springframework/transaction/event/TransactionalEventListener.html).

감사 실패 정책도 테스트한다. 주 쓰기가 이미 커밋된 뒤 audit insert가 실패했다고 HTTP를 업무 rollback500처럼 반환하면 재시도 중복을 유발할 수 있다. 커밋된 업무 응답은 사실대로 유지하고, 감사 실패를 민감값 없는 오류 이벤트/운영 신호로 남기는 정책을 명시한다. 실패 기록의 유실을 조용히 통과로 표시하지 않는다. 프로세스 종료 사이의 영구 전달 보장은 이 synchronous adapter만으로 주장하지 않고 012 outbox/관측/운영 검증과 구분한다. 감사 보존/삭제 정책·운영 조회 제한도012에서 마무리한다.

Starter는 Reference audit code를 import하지 않고 자체 선택 설정·migration/합성 자료로 동일 SPI/adapter를 소비하는 테스트를 제공한다. 기본 최소 앱의 Flyway 비활성·업무 테이블 없음은 유지할 수 있으며, 선택 감사 모드의 H2 준비와 소비 검증을 따로 기록한다. 등록만 된 noop와 Reference 전용 adapter만으로 공통 감사 소비 완료를 주장하지 않는다.

## 오류·보안·API 테스트 경계

기존 신규 오류의 항상 존재하는 `code/message/errors[]` 형식을 유지한다. 원본 업무 code는 INVALID_INPUT·FORBIDDEN·NOT_FOUND·REVISION_CONFLICT·DATA_CONFLICT다. 원본 Security의 LOGIN_FAILED/UNAUTHENTICATED와 신규의 AUTH_FAILED/AUTH_REQUIRED 차이는 구분하여 기록하며, 007 업무를 추가했다고 기존 Starter 인증 코드를 임의 교체하지 않는다. 오류 message에 제출 값·SQL·내부 경로·hash를 넣지 않는다.

공통 Advice 보강 후보는 낙관 잠금409, 데이터 중복/FK409, 누락 parameter/잘못된 형식400, 업무 denied403, 없는 asset404, method405, Content-Type415, 알 수 없는500이다. catch-all은 예외 message 전체를 응답/로그에 복사하지 않는다. controller Advice 순서/적용 범위를 확인해 앱 Advice와 기본 빈이 동시에 같은 예외를 다루지 않게 한다. 필터의 CSRF/인증 JSON은 Advice 밖의 별도 경계로 회귀 검사한다.

원본에는 세션 유휴/절대 수명·CSP가 추가되어 있지만 현재 신규 chain은 같은 완성도라고 주장할 수 없다. 007은 현재 신규 세션/CSRF와 actor 권한을 보존하며, 원본 세션 timing/연장·CSP 전체 복제는 구현/검증 범위를 별도로 정해010/012 기록에 남긴다. 브라우저 localStorage에 JWT/비밀번호를 저장하지 않는다. dev Swagger 외의 공개 문서를 자동 활성화하지 않는다.

## 구현에 넘길 파일 목록과 남은 결정

007 실제 착수 전에 아래 목록을 담당별로 나누되 설치/전체 format/build/JAR 검증은 root가 순차 실행한다.

- 공통: session endpoint 분리와 속성 metadata, security/Advice 감사 연결, 감사 core SPI·중립 H2 adapter·auto-config·소비 ContextRunner 테스트.
- Reference backend: DB users/bootstrap/ActorResolver/SessionController/User DTO·사용자 API; Menu DTO/API; Requirement Entity/Repository/Input/Response/Mapper/Service/Controller·migration V2/V3·권한/rollback/동시성 테스트; ADMIN 감사 조회.
- frontend 공통 runtime: 기본 호환 session decode 확장·단일 원본·generic public 타입·session generation/401/Query 회귀. 업무 imports 없음.
- Reference frontend: `features/requirements`의 generated DTO/API/schema/query keys/폼/검토/댓글/이력/페이지; Router·SPAforward·메뉴·Day.js표시. sourcequery를 작성 중 폼에 자동 복사하지 않음.
- Starter: 기존 업무 없는 기본 앱의 계약 회귀와 선택 audit adapter 소비 예제/테스트. Reference 업무 코드 import 없음.
- 문서/산출물: api/folder/maintenance/operations·OpenAPI와 생성 타입·007검증 로그·Day.js버전/라이선스·실패/남은010/012경계.

확정할 구체 사항은 session decode public generic 타입/주입, 앱별 OpenAPI 산출물 분리 위치, H2 시각 정밀도, 같은 시각 명령의 요청 version 증가 방법, 선택 Starter audit migration 활성 방식, audit 실패의 운영 신호다. 각 항목은 여기 제안과 의미 있는 테스트를 바탕으로 구현 시 결정한다. 이 문서 작성 완료만으로 Entity·SPI·날짜·감사·업무 E2E·007 단계가 구현/실행 완료된 것은 아니다.
