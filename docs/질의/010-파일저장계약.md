# 010 미디어·파일 서버 구현 계약

이 문서는 010 서버 소유 범위의 구현 인계 자료다. 서버 테스트와 Starter 저장소 CLI, Reference clean restart·UI 최종 통합 검증까지 실제 통과했다. 단계 완료 상태와 실제 성적은 [010 업무 확장 계획](010-업무확장과파일작업실.md)의 최종 근거를 따른다.

## 공통 저장소와 소비 앱

| 부품                             | 공개 책임                                                                               | 소비 앱의 책임                                              |
| -------------------------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `FileStorage`                    | `write(InputStream, maxBytes)` → `StoredBlob(key, size)`, `open`, `exists`, `delete`    | 권한, 원본 이름, MIME 검사, metadata, 파일과 업무 연결      |
| `LocalFileStorage`               | opaque UUID key, 제한을 적용한 스트리밍, 일반 파일/NOFOLLOW 검사, 실패한 부분 파일 정리 | 명시적 저장 root 지정, DB와 uploads 동시 백업               |
| `FileStorageTransactions`        | rollback 시 새 파일 삭제, commit 이후 기존 파일 삭제, 정리 실패 계수                    | 실제 DB transaction 안에서 등록, 운영 경보·012 정리 정책    |
| `ScFileStorageAutoConfiguration` | 기본 비활성, 소비자 SPI bean이 있으면 backoff                                           | `sc.framework.file-storage.enabled/root/max-bytes` 설정     |
| Reference                        | 영속 H2 파일 metadata와 화면·버전·요구사항 연결                                         | V4 migration, 작성자/담당자 권한, revision, 이력·감사       |
| Starter `file-storage`           | 공통 SPI의 독립적인 두 번째 소비 예제                                                   | 현재 실행의 in-memory whitelist, ADMIN·세션·CSRF, 종료 정리 |

root 생성은 첫 쓰기까지 지연한다. 앱 구성만 읽거나 Starter 기본 프로필을 실행하면 파일 저장 root를 만들지 않는다. Reference root는 `SC_UPLOAD_DIR`로 분리하며 개발·배포·E2E가 각자의 runtime를 사용한다. API에는 내부 경로나 저장 key를 Reference 업무 DTO에 넣지 않는다. Starter demo의 key는 현재 실행의 whitelist에서만 유효한 opaque 식별자이며 영속 업무 metadata를 제공하지 않는다. 공통 모듈과 Starter는 Reference 클래스·DDL을 가져오지 않는다.

업로드 제한은 10 MiB다. 공통 adapter는 소비자 한도와 설정 한도 중 작은 값을 실제 읽은 bytes에 적용하고, 실패한 쓰기는 부분 파일을 삭제한다. `write`에 전달한 입력 stream의 종료는 호출자가 담당한다. `open`의 반환 stream은 HTTP resource 처리 등 소비자가 종료한다.

ADO 연결은 수동 metadata 기록이다. 외부 ADO API·계정·토큰을 호출하지 않는다. ADMIN이라는 이유로 타인 요청을 편집하거나 ADO 연결을 덮어쓸 수 없다. ticket은 영숫자·`_`·`-` 1~80자이며 URL은 host가 있는 HTTP/HTTPS, user-info 없이 2,000자 이하다. 같은 revision으로 다시 저장하면 409이고 입력 재확인 책임은 앱 폼에 둔다.

요구사항 생성은 화면 버전/박스를 함께 지정하거나 모두 생략한다. 화면 버전은 해당 메뉴에 속해야 하며 생성 후 다른 버전으로 바꿀 수 없다. 보관 버전의 기존 요청은 조회·본문/박스 편집을 유지하고 새 요청 생성은 거절한다. 기존 본문 PUT은 동일 `screenVersionId`와 박스를 전달하면 연결/박스를 유지하며, 박스를 명시적으로 null로 전달하면 삭제한다. 박스 없는 이미지 요청은 검토 요청으로 전환할 수 없다.

버전 번호는 화면 부모 잠금과 증가 counter로, 박스 번호는 버전 부모 잠금과 증가 counter로 예약한다. 삭제한 박스 번호를 다시 사용하지 않는다. 요청 revision CAS를 확보한 뒤 박스·첨부 등 자식을 변경하며 rollback에서는 본문·자식·이력과 성공 감사가 부분 반영되지 않는다.

## 실제 파일과 이미지 좌표

Reference는 실제 decode 가능한 PNG/JPEG와 `%PDF-` signature의 PDF만 허용한다. 확장자와 전달 MIME을 신뢰하지 않고 서버가 판정한 MIME을 응답한다. 이미지는 한 변 12,000, 전체 40,000,000 pixels를 초과하면 거절한다. PDF signature 검사에는 악성 콘텐츠 검사나 PDF 전체 의미 검증이 포함되지 않는다. 이름은 경로 부분·제어 문자를 제거하고 180자 안에서 표시용으로만 저장한다.

원본 image bytes는 변환·재압축하지 않는다. JPEG APP1 EXIF의 TIFF byte order, IFD offset/count와 orientation 1~8을 제한적으로 검증한다. 5~8에서는 공개 width/height를 교환한다. 0~1 박스 좌표는 **내장 방향이 적용된 원본 이미지의 표시 축**을 기준으로 하며 축을 다시 회전하지 않는다. 브라우저 `naturalWidth/naturalHeight`는 방향 metadata 적용을 포함하지만 JDK JPEG plugin은 EXIF APP1을 일반 unknown marker로 다루므로 별도 해석을 구현했다. [HTML image 크기 명세](https://html.spec.whatwg.org/multipage/embedded-content.html#dom-img-naturalwidth), [JDK 21 JPEG metadata 명세](https://docs.oracle.com/en/java/javase/21/docs/api/java.desktop/javax/imageio/metadata/doc-files/jpeg_metadata.html).

PNG eXIf는 기본 orientation 1만 지원한다. 회전·반전 PNG는 구체적인 안전 400 오류로 거절하며, EXIF payload가 65,533 bytes를 넘거나 손상된 offset/endian/type/count/value는 거절한다. JPEG/PNG의 모든 vendor metadata를 해석한다고 주장하지 않는다. 좌표는 유한값이고 `x/y` 0~1, `width/height` 0 초과~1, 박스 끝이 이미지 안에 있어야 한다. normalized 원본 박스를 저장하며 CSS zoom이나 캔버스 pixels를 DB에 넣지 않는다.

## DB·파일 수명과 이관

V1~V3 원문을 수정하지 않는다. V4는 H2 catalog에서 V2의 `screen_version_id IS NULL` CHECK 이름을 찾고 제거한 뒤 실제 버전 FK를 추가한다. constraint 이름을 추측하거나 SQLite SQL을 재사용하지 않는다. H2의 `EXECUTE IMMEDIATE`와 `QUOTE_IDENT`는 자체 schema metadata에만 적용한다. [H2 EXECUTE IMMEDIATE 문서](https://h2database.com/html/commands.html#execute_immediate).

V4의 tables는 `stored_file`, `screen_entry`, `screen_version`, `requirement_annotation`, `requirement_attachment`, `requirement_ado`다. annotation은 요청당 하나, 버전별 번호 unique, version은 화면별 번호 unique다. Starter에는 이 DDL을 적용하지 않는다.

DB rollback에서는 먼저 저장한 새 파일을 정리한다. 첨부 삭제는 metadata commit 뒤 실제 파일을 정리한다. 이때 I/O 실패가 이미 commit된 HTTP 결과를 500으로 바꾸지 않으며, 예외 내용·파일 key·경로를 출력하지 않고 bounded 운영 로그와 `cleanupFailures()` 계수를 남긴다. 프로세스 중단 사이의 orphan 파일, crash를 포함하는 영속 삭제 큐와 재시도, 백업/복원 세트 검증은 012에서 추가한다. 현재 계수만으로 영속 정리 보장을 주장하지 않는다.

## schema 변화와 검증 인계

기존 상세 JSON의 nullable 자리와 배열을 유지한다. 010 이전에 사용되지 않던 `RequirementAnnotationResponse`, `RequirementScreenVersionResponse`, `RequirementAttachmentResponse`, `RequirementAdoResponse`는 실제 값을 반환하도록 필수 필드·날짜·범위를 구체화했다. 이는 placeholder schema의 의도적인 강화이며 이전 모든 생성 타입이 그대로라는 뜻이 아니다. 새 capture/type 생성과 실제 schema 비교 결과는 root가 010 근거에 기록한다.

이 범위의 실제 통과 테스트는 공통 저장소 7개, EXIF 2개, Reference 미디어 10개, V4 migration 2개, Starter 선택 소비 2개와 기존 기본 소비 테스트에 추가한 비활성 검사 1개다. 전역 합계에 별도로 더하지 않는다. [서버 네 번째 실행](../검증/010-server-tests-fourth.log)은 core 3 + autoconfigure 27 + Reference 105 + Starter 8 = 143개를 실패·오류·skip 없이 통과했다. 이후 [fresh 다섯 번째 통합 빌드](../검증/010-integration-build-fifth.log)도 서버 143개와 프런트 단위 135개/33파일을 통과했으며, 두 fresh JAR와 각 앱 dist bytes 일치를 [산출물 결과](../검증/010-server-and-artifacts-fifth.json)에 기록했다. 이 성적은 UI 최종 기능·접근성·시각 QA가 완료됐다는 뜻으로 확대하지 않는다.

초기 검증에서 query revision 0의 오류가 generic 500이 되는 문제와 archived Swagger 숫자 enum/type이 잘못 생성되는 문제가 드러났다. 공통 Advice의 MVC 메서드 검증 400 처리와 기존 OpenAPI numeric flag 보강을 적용하고 실제 Reference 재검증에서 해결을 확인했다. Starter 새 테스트는 private bootstrap secret 설정이 없어 기동하지 못했으며, 자기 임시 secret/600 권한과 명시적인 합성 사용자 인증 provider를 추가했다. 또한 성공한 쓰기 뒤 입력 stream 종료 실패 경로에서 원본 blob/whitelist를 정리하도록 두 소비자를 보강하고 실제 close 실패 stream 테스트를 추가했다. 이 보강과 Starter 기동 수정은 서버 네 번째 실행과 fresh 다섯 번째 통합 빌드에서 실제 통과했다. 첫 실패와 재검증 로그는 삭제하지 않는다.

`scripts/verify-starter-storage.py`의 [실제 CLI 결과](../검증/010-starter-storage.json)는 8개 검증 그룹을 통과했다. [실행 로그](../검증/010-starter-storage.log)와 [명령 출력](../검증/010-starter-storage-command-first.log)을 보존한다. `run.sh`를 실제 거치는 default와 `file-storage`, `dev,file-storage`, `prod,file-storage`, `audit,file-storage`, `dev,audit,file-storage`, `prod,audit,file-storage` 조합을 자기 임시 H2/root/합성 secret으로 검사했다. 잘못된 조합·Reference의 Starter 전용 프로필은 runtime 생성 전에 거절됐고, 실제 launcher PID/TERM/잠금 해제, 세션·CSRF·원본 bytes·한도·headers·UUID/whitelist·종료 파일 정리·재기동 whitelist 차단·Swagger를 확인했다. 임시 폴더 제거와 합성 비밀값 미출력도 결과에 기록했다. 배포 Starter bootstrap은 ADMIN 하나이므로 non-ADMIN 거절은 실제 통과한 MockMvc 합성 두 역할 사용자 fixture의 근거이며, 이 CLI에서 non-ADMIN HTTP를 실행했다고 주장하지 않는다.

`scripts/verify-reference-media.py`는 root가 fresh Reference JAR로 실제 실행했으며 [5개 그룹 결과](../검증/010-reference-media-restart.json)가 모두 통과했다. [실행 로그](../검증/010-reference-media-restart.log)와 [명령 출력](../검증/010-reference-media-restart-command-first.log)을 보존한다. 별도의 임시 H2/uploads에서 이미지 버전·정규화 박스 요구사항·PDF 첨부를 생성하고, 동일 자료의 clean stop/start 뒤 작성자 identity·metadata·revision 2·버전·원본 image/PDF bytes가 동일함을 확인했다. ADMIN의 타인 첨부 삭제는 거절됐으며 작성자의 실제 삭제 뒤 revision 3/file 404/PDF blob 제거와 원본 이미지 유지도 확인했다. 정상 종료와 임시 폴더 제거, 합성 자격 증명 로그 미출력까지 통과했다. Starter의 비영속 whitelist 재기동 결과와 Reference의 영속 metadata 재기동 결과를 혼동하지 않는다. 이 검증은 clean stop/start이며, crash를 포함한 영속 정리 큐와 일관된 백업/복원은 계속 012 미완료 범위다.
