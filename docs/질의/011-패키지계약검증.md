# 011 패키지 계약 검증

현재 상태는 **011 구현·로컬 통합 검증 완료**다. 실제로 빌드한 5개 npm tarball과 4개 Maven 좌표의 7개 파일을 검사했고, repository 밖의 소비 앱 설치·cold build·JAR/브라우저·0.1.0→0.2.0→0.1.0 변경을 실제 확인했다. 검증기 작성, tarball 검사, 외부 소비 앱 실행은 별도 증거로 기록한다. Redis·JWT·SSO 제외, 업무 코드와 공통 패키지 분리, `Sc` 공통 UI 네이밍은 유지한다. 012 운영 모듈·crash 복구·backup은 이번 완료 범위에 포함하지 않는다.

전체 배포 설계는 [011 공통 패키지 배포 설계](011-공통패키지-배포설계.md), 생성기 준비는 [011 배포와 생성기 준비 검토](011-배포와생성기-준비검토.md), 공개 UI 기준은 [UI 공개 계약](UI-공개계약.md)을 따른다. 이 문서는 실제 산출물의 구조와 실패 차단을 다룬다.

생산기와 검사기의 기준은 별도 구현 책임을 가진다. 검사기는 `build-manifest.json`의 형식·이름·버전·64자리 입력 digest를 확인한다. 현재 소스와 입력 digest가 같은지는 생산·pack 단계에서 확인한다. 따라서 0.2.0으로 버전을 올린 뒤 보존한 0.1.0 tarball을 검사할 때, 이전 정상 stamp를 현재 소스 stamp라고 오인하지 않는다.

## 입력 manifest

`artifacts.json`은 `format: 1`, `templateVersion: 1`, `frameworkVersion`을 가진다. `frontend`에는 `@sc/ui`, `@sc/runtime`, `@sc/date`, `@sc/excel`, `@sc/i18n`이 각각 하나씩 있어야 한다. 각 항목은 `name`, `version`, `file`, `sha256`을 가진다. 프런트 버전은 frameworkVersion과 같고 tarball 이름은 `sc-ui-0.1.0.tgz`와 같은 규칙을 따른다.

`backend.repository`는 `maven`, 버전은 frameworkVersion에 `-SNAPSHOT`을 붙인 값이다. 좌표는 `dev.scframework` 그룹의 `sc-framework-parent`, `framework-core`, `framework-autoconfigure`, `framework-spring-boot-starter`다. 부모 POM 1개와 나머지 모듈의 POM·일반 JAR 각 1개로 **POM 4개·JAR 3개**를 검사한다. 앱의 실행 JAR와 Reference 업무 클래스를 프레임워크 배포 좌표로 제공하지 않는다.

`toolchain`은 현재 Node `24.16.0`, npm `11.13.0`, Java `21`, Spring Boot `3.5.16`을 명시한다. 이 필드는 JSON 주장만으로 해당 도구의 실제 실행을 입증하지 않는다. 실제 생산·소비 실행 로그가 별도로 필요하다.

파일 경로는 artifact root 안의 정규 파일이어야 하며, 경로 구성 요소의 symlink, 절대 경로, `..`, 빈 경로를 거절한다. 모든 tarball·Maven 파일은 manifest SHA-256과 일치해야 한다. npm 5개 또는 Maven 7개를 누락하거나 빈 목록으로 성공할 수 없다.

패키지 루트의 `types`는 `./dist/types/index.d.ts`다. JS export는 `types` 조건을 먼저 두고 `import`, `default`를 같은 ESM JS에 연결한다. UI subpath 선언은 `dist/types/table/index.d.ts`와 같은 위치다. `./styles`는 선언과 `./dist/sc-ui.css`, `./tokens`는 `sass`·`default` 모두 `./dist/tokens.scss`에 연결한다. 구체적인 export target이 실제 tarball에 존재해야 한다. private source·dist 경로를 별도 public export로 추가하면 실패한다.

조건부 exports의 해석과 상대 ESM 파일 확장자는 [Node 24.16 패키지 문서](https://nodejs.org/download/release/v24.16.0/docs/api/packages.html#conditional-exports)를, 타입 해석의 exports 경계는 [TypeScript 모듈 참조 문서](https://www.typescriptlang.org/docs/handbook/modules/reference.html#packagejson-exports)를 기준으로 한다. 외부 앱은 공개 package/subpath를 가져오고 workspace alias나 원본 source 경로에 의존하지 않는다.

## tarball과 모듈 검사

tarball은 압축 해제 크기를 128 MiB, 개별 entry를 32 MiB로 제한하고 checksum·entry 크기·종료·중복 경로를 검사한다. `package/` 아래의 정규 파일·디렉터리만 허용한다. symlink·hardlink·특수 entry·경로 탈출·일관되지 않은 PAX size를 거절한다. 검사한 정규 파일은 격리된 임시 폴더에만 추출하고 성공·실패 모두 정리한다. 패키지 코드를 실행하여 안전 여부를 판정하지 않는다.

배포 allowlist는 `dist`, `README.md`, `UNLICENSED`, `THIRD_PARTY_NOTICES`다. 원본 `.vue`·`.ts`, 테스트·Story·앱 폴더, `source-entries.json`, map, DB·업로드·비밀 파일·실행 JAR는 tarball 안에서 거절한다. `package.json`의 `files`도 같은 allowlist여야 한다. 소비 설치 중 소스 빌드를 유발하는 `prepare`·`preinstall`·`install`·`postinstall`을 제공하지 않는다. pack 동작 자체는 [npm 11 pack 문서](https://docs.npmjs.com/cli/v11/commands/npm-pack/)에 따른다.

모든 배포 JS와 `.d.ts`를 TypeScript AST로 파싱한다. static import/export, literal dynamic import, import type, import equals, 선언 reference를 읽는다. 상대 참조는 전달된 확장자를 가지고 같은 tarball의 `dist` 파일로 연결되어야 한다. 선언의 `./component.vue.js`는 대응 `.vue.d.ts`를, `./generated/api.js`는 `.d.ts`를 확인한다. `.mjs`·`.cjs` 선언 참조에는 `.d.mts`·`.d.cts`가 있어야 하며 JS 파일만 있는 것으로 대체하지 않는다. 비 literal dynamic module 참조, 절대 경로·workspace source alias, 선언되지 않은 bare dependency, 설치 vendor가 공개하지 않은 subpath를 거절한다.

JS·타입 파일과 루트의 실제 named export가 각각 존재해야 한다. 상대 `export *`는 AST의 배포 파일 graph를 따라 합성하며 순환 경로를 제한한다. UI 컴포넌트는 value export여야 하므로 `export type`의 named·star 재노출을 value로 세지 않는다. 빈 JS와 빈 선언을 함께 제공하는 것은 완료가 아니다. UI 22개 공개 컴포넌트의 JS·선언 export가 지정한 entry에 있고 `CONTRACTS.json`이 현재 공개 snapshot과 같아야 한다. CSS의 실제 `sc-*` 선택자·`--sc-*` 토큰, Sass의 768px 기준과 `$sc-emit-css` 기본값, CSS·SCSS의 side effect를 확인한다. CSS 외부 URL·누락된 상대 asset도 거절한다.

## 의존성과 라이선스

자체 코드의 `private: true`, `UNLICENSED`를 유지하며 이름만 바꾸어 공개 OSS 라이선스로 전환하지 않는다. 직접 dependency·peer·optional dependency는 exact 버전이어야 한다. 각 Sc 패키지 위치에서 실제 vendor를 resolve하여 이름·버전·라이선스를 읽고 compiled manifest와 비교한다. UI의 Floating UI처럼 package-local 버전이 루트 transitive 버전과 다른 경우에도 UI 기준을 검사한다.

`THIRD_PARTY_NOTICES`에는 직접 vendor 이름·실제 버전·라이선스와 설치 패키지의 원본 LICENSE·COPYING·NOTICE 텍스트가 있어야 한다. ECharts의 Apache LICENSE·NOTICE도 포함한다. vendor JS는 bare import로 외부화하므로 이 파일을 모든 npm transitive 라이선스의 완전한 목록이라고 설명하지 않는다. 소비 앱이 설치하는 vendor와 그 transitive 패키지의 원래 고지도 함께 적용된다.

011에서 Vue I18n은 기존 `11.4.13`의 선언 호환 문제를 확인하여 중앙 manifest·lock을 `11.1.12`로 변경했다. 그 published 선언의 `@intlify/devtools-types` 참조에는 같은 버전 `11.1.12`를 직접 dependency로 추가했다. 실제 생산기·검사기·외부 consumer 실행 증거로 변경 이후 상태를 확인한다. UI 생산 선언 검사에서는 vendor 선언 오류 때문에 `skipLibCheck: true`를 사용하되 자체 source의 strict 검사는 유지한다. 최초 `false` 실행의 697개 vendor 진단은 보존하며 vendor 타입을 patch하거나 오류를 `any`로 덮지 않는다. 다른 4개 패키지의 선언 검사와 외부 consumer probe 결과는 별도로 기록한다.

검사기의 AST 참조·public export 검사는 전체 vendor의 타입 의미 검사나 소비 앱의 Props 사용 검사와 같지 않다. 외부 consumer의 정상 타입·빌드·브라우저 실행, 잘못된 public Props와 private import의 compile 실패, UI vendor `skipLibCheck: false` probe는 011 통합 검증의 별도 근거다. native Node UI import·SSR 지원을 이 검사만으로 보장하지 않는다.

현재 0.2.0 외부 [타입 소비 JSON](../검증/011-consumer-types-v02.json)은 public 타입 12개 probe·중립 native library 4개·private import 3개 거절·Sass를 통과했다. UI `skipLibCheck:false` probe의 실제 vendor 진단은 **696개**, own source 진단은 **0개**다. 최초 생산의 697개와 다른 실행 결과이므로 과거 숫자를 바꾸지 않는다. non-UI 4개 패키지의 `skipLibCheck:false` strict probe는 exit0이다. UI vendor strict 한계를 해결했다고 기록하지 않고, 공개 타입 오용을 각각 실제 compile 실패로 확인한 결과와 함께 제공한다.

## 실행과 재사용 API

아래 명령은 실제 pack 완료 후 입력 폴더를 지정하여 실행한다. 예시 경로는 실행 자료를 생성하라는 의미가 아니며, 정상 tarball 대신 fixture를 정상 제품으로 사용하지 않는다.

```sh
node scripts/verify-package-artifacts.mjs \
  --artifacts /absolute/path/to/compiled-artifacts \
  --report docs/검증/011-package-artifacts.json

node scripts/verify-package-gates.mjs \
  --artifacts /absolute/path/to/compiled-artifacts \
  --report docs/검증/011-package-gates.json
```

`--report`는 artifact·source 입력을 덮어쓸 수 없다. 검사 결과는 JSON과 짧은 고정 오류 코드로 남긴다. package 코드·파일 내용·비밀번호·토큰을 콘솔에 출력하지 않는다.

생성기는 `verifyArtifactDirectory(artifactRoot)`를 같은 스크립트에서 import하여 재사용한다. 성공하면 `{ manifest, report }`를 반환하고 실패하면 `PackageArtifactError.code`를 포함한 고정 오류를 던진다. 모듈 import 시 CLI는 자동 실행하지 않는다. 생성기 dry-run도 검사를 생략하지 않으며, 생성 앱에 검사기 구현을 복제하지 않는다. 검증한 vendor 파일과 provenance manifest를 전달하는 것과 실제 앱 설치·실행은 구분한다.

## 실제 실패 CLI 검증

부정 검증은 먼저 루트가 실제 빌드·pack한 전체 제품이 검사 CLI를 통과하는지 확인한다. 그 tarball을 격리된 임시 폴더로 복제하고 위반 하나를 넣은 뒤 tar·manifest SHA를 재생성한다. 실제 checker subprocess가 0이 아닌 상태와 기대한 고정 오류를 반환하고 임시 추출을 지운 경우에만 해당 case를 통과로 기록한다. 정상 source·manifest·lock·UI snapshot·생산 helper·원본 artifact는 변경하지 않으며 전후 SHA를 비교한다.

| 변조                                                            | 기대하는 실패 코드                                   |
| --------------------------------------------------------------- | ---------------------------------------------------- |
| public JS export target 삭제                                    | `SC_PACKAGE_EXPORT_MISSING`                          |
| static import·re-export·literal dynamic import의 상대 파일 삭제 | `SC_JS_RELATIVE_MISSING`                             |
| 선언되지 않은 bare vendor                                       | `SC_JS_UNDECLARED_BARE`                              |
| workspace source alias import                                   | `SC_JS_ABSOLUTE_ALIAS`                               |
| raw source·DB·source map 포함                                   | `SC_PACKAGE_FORBIDDEN_FILE`                          |
| UI private export 추가                                          | `SC_PACKAGE_PRIVATE_EXPORT`                          |
| UI 컴포넌트를 named·star type-only export로 변경                | `SC_UI_COMPONENT_EXPORT`                             |
| public CSS 삭제                                                 | `SC_UI_CSS_MISSING`                                  |
| 선언 absolute path·dangling relative type                       | `SC_DECL_ABSOLUTE_ALIAS`, `SC_DECL_RELATIVE_MISSING` |
| root JS·선언의 named export 제거                                | `SC_PACKAGE_EMPTY_MODULE`                            |
| 자체 권리 파일 누락                                             | `SC_PACKAGE_NOTICE`                                  |
| 직접 vendor를 범위 버전으로 변경                                | `SC_VENDOR_EXACT_VERSION`                            |
| 생산 stamp digest 변조                                          | `SC_PACKAGE_BUILD_STAMP`                             |
| tar 경로 탈출·절대 경로                                         | `SC_TAR_PATH`                                        |
| symlink·hardlink                                                | `SC_TAR_LINK`                                        |
| tar 중복 entry                                                  | `SC_TAR_DUPLICATE`                                   |
| frontend artifact 0개                                           | `SC_ARTIFACT_FRONTEND_COUNT`                         |

명령이 실패했지만 기대한 코드가 다르면 검증을 통과시키지 않는다. report에는 실패 phase·실제 코드·경계 context를 보존한다. 이를 수정 없이 정상 성공으로 바꾸거나 앞단 다른 오류를 의도한 실패라고 기록하지 않는다.

## 최초 실제 산출물 검사 결과

최초 `v0.1.0` actual pack에 대한 CLI는 exit 1이었다. [초기 로그](../검증/011-package-artifacts-first.log)와 [초기 JSON](../검증/011-package-artifacts-first.json)을 보존한다. `@sc/ui`의 `dist/types/table/model.d.ts`에 `@tanstack/table-core` import type이 있었지만 packed manifest의 직접 dependency·peer에 없어서 `SC_DECL_UNDECLARED_BARE`로 차단했다. 후속 읽기 점검에서는 `useVirtualRows.d.ts`의 `@tanstack/virtual-core` 참조도 같은 문제로 확인했다. 설치 버전 `9.2.6`, `3.17.11`을 direct dependency와 고지에 반영한 candidate2가 후속 AST CLI를 통과했다.

이 실패는 UI vendor의 `skipLibCheck` 진단과 다른 자체 배포 선언의 참조 계약 결함이다. transitive 의존성을 직접 선언으로 간주하여 통과시키지 않았다. 최초 release 폴더를 다시 쓰지 않고 exact dependency·고지·생산 stamp를 갱신한 `v0.1.0-candidate2`를 검사했다.

## CI 구성과 확인 경계

[verify.yml](../../.github/workflows/verify.yml)의 기존 검증 job은 `SC_EVIDENCE_STAGE=011`과 세 자리 processor stage `011`을 사용한다. 기존 001~010 evidence upload 경로를 유지하고 011 경로를 추가했다. `contents: read`와 Ubuntu 24.04·Node 24.16.0·npm 11.13.0·JDK 21을 사용한다. `shell: bash`를 명시하여 `tee` 뒤에서도 앞 명령 실패가 job 실패로 이어지게 한다. shell과 job 의존성은 [GitHub workflow 구문](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_iddefaultsrun), evidence 전송은 [공식 upload-artifact](https://github.com/actions/upload-artifact/blob/main/README.md)를 기준으로 한다.

별도 `package-consumer` job은 기존 `verify`가 성공한 뒤 같은 commit을 새 runner에서 받는다. 다음 순서로 실제 제품을 다시 생산하고 소비하도록 구성했다.

1. root `npm ci`와 공통 패키지 5개 생산 빌드
2. `RUNNER_TEMP`의 private canonical 폴더에 producer 전용 Maven 저장소를 만들고 공통 4좌표만 `clean install`하여 실제 공통 테스트 실행
3. 실제 pack → artifact CLI → 부정 archive CLI → 실제 artifact를 사용하는 generator CLI
4. repository 밖의 새 경로에 실제 standalone Starter 생성 후 consumer `npm install`로 독립 lock 생성
5. producer와 다른 consumer Maven local repo를 `MAVEN_OPTS`로 지정하고 generated `scripts/build.sh` 실행
6. 공개 타입·잘못된 Props/emit/slot·private import·중립 native API·Sass 검사와 실제 JAR의 세션/CSRF·H2 clean restart·설치 UI 브라우저 검사
7. generated optional profile·600 secret·PID ownership·자기 dev launcher/정상 종료 검사를 추가로 실행
8. 명시한 공개 산출물·테스트·redacted evidence만 보관한 뒤 해당 job의 generated 프로젝트·두 Maven 캐시 정리

생성 앱은 자기 `backend/mvnw`를 사용하고 vendor repository 위치의 해석은 generated Wrapper·설정 파일의 책임으로 둔다. CI가 프레임워크 reactor나 producer Maven cache를 consumer 캐시로 복사하지 않는다. 부모 POM의 최초 해석과 local repo override의 실제 동작은 별도 외부 consumer 실행 로그로 확인한다.

`build.sh` 안의 첫 `maven.test.skip=true` package는 업무 API 수집을 위한 중간 metadata 빌드다. 뒤의 실제 API 수집·npm 검증과 최종 `clean verify`가 성공해야 CI 소비 빌드를 통과한다. metadata 성공을 테스트 성공이라고 기록하지 않는다. UI vendor strict 진단과 native Node UI·SSR 미지원 경계도 소비 검증에서 유지한다.

CI는 generated `.runtime`·H2·업로드·bootstrap secret을 통째로 수집하지 않는다. 배포 manifest·npm tarball·Maven POM/일반 JAR, 명시한 test/provenance/lock과 안전한 증거만 지정한다. Mac 시각 baseline을 Linux pixel baseline으로 사용하거나 자동 갱신하는 단계는 추가하지 않았다.

[최초 로컬 YAML JSON](../검증/011-ci-yaml.json)의 Bash35·Python3·processor `--stage 011 --help` 확인을 보존한다. 새 generated feature step 이후 [최신 CI 정적 JSON](../검증/012-preparation-ci-check.json)은 installed `js-yaml` 파싱·Bash36개의 `bash -n`·embedded Python3 AST·실제 script의 `--app`/`--label` 연결을 확인했다. 이 검사는 job 명령을 실행하지 않았으며 Maven·install·브라우저 성적을 대신하지 않는다. **GitHub 원격 CI와 Linux consumer 실행은 아직 미실행**이다.

원격 publish, 원격 CI 실행, Linux 시각 baseline, Docker daemon 기반 배포, 수동 VoiceOver, 012 운영 모듈·crash 복구·backup 검증은 이 표의 양성 tarball 검사로 완료되지 않는다.
