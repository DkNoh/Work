# 012 예약과 브라우저 오류

이 문서는 2026-10-07에 작성한 서버 구현 계약과 검증 위치를 설명한다. 012 전체 완료 문서가 아니다. 실제 운영 JAR 검증은 Root가 새 JAR를 준비한 뒤 순차 실행하며, 아래 작성된 검사 수를 실행 성공 수로 읽지 않는다. Redis·JWT·SSO는 도입하지 않는다.

## 활성과 책임

`sc.framework.scheduler.enabled`와 `sc.framework.browser-errors.enabled`는 기본 `false`다. 두 앱의 `operations` 프로필이 기능과 앱 소유 Flyway DDL을 함께 활성화한다. 일반 앱 세션·CSRF 계약은 유지하며, 인증 후 `/api/framework/capabilities`의 `scheduler`·`browserErrors` 값을 보고 프런트 설치 여부를 판단한다. 프레임워크 버전과 소비 앱의 `app-version=0.1.0`은 별개다.

| 책임                               | 구현 위치                                                                                                                                        |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 등록 작업 공개 계약                | `backend/framework-core/src/main/java/dev/scframework/core/scheduling/`                                                                          |
| Quartz 등록·예약·실행·이력         | `backend/framework-autoconfigure/src/main/java/dev/scframework/autoconfigure/ScSchedulerAutoConfiguration.java`, `scheduling/`                   |
| 중립 오류 수집·크기/형식/횟수 제한 | `backend/framework-autoconfigure/src/main/java/dev/scframework/autoconfigure/ScBrowserErrorsAutoConfiguration.java`, `browsererrors/`            |
| 현재 DB actor와 ADMIN 검사         | Reference `operations/scheduling/OperationalScheduleController.java`, `operations/browsererrors/BrowserErrorsController.java`                    |
| 현재 인증 provider의 subject/역할  | Starter `operations/scheduling/StarterOperationalActor.java`와 두 Controller                                                                     |
| 앱 소유 DDL                        | Reference `db/operations-migration/V7__operations_scheduler_browser.sql`, Starter `db/operations-migration/V3__operations_scheduler_browser.sql` |

Reference의 기존 업무 migration V1~V5를 변경하지 않는다. 두 앱의 V6/V2 메시징 schema는 별도 담당 범위다. 이 migration에는 Quartz 공식 H2 table 11개와 앱 운영 table 6개가 있다. 공식 DDL의 DROP·COMMIT은 제외하고 Flyway가 최초 생성과 버전을 관리한다. `initialize-schema=never`이며 `useProperties=true`로 등록 JobDataMap에 문자열만 저장한다.

## 작업 등록과 실행 경계

공개 SPI는 `RegisteredOperationalTask.jobCode()`, `executionMode()`, `execute(ScheduledRunContext)`다. 실행 문맥에는 canonical UUID `runKey`, 등록 `jobCode`, 숫자 `scheduleId`, 서버 UTC micro `scheduledAt`, 양수 `attempt`만 전달한다. 사용자에게 Java class·bean 이름·Serializable payload·Calendar 입력을 받는 HTTP는 없다.

| 등록 코드         | 모드                | 기본 예약                                |
| ----------------- | ------------------- | ---------------------------------------- |
| `OUTBOX_DISPATCH` | `NON_TRANSACTIONAL` | ID 1, `0 * * * * ?`, UTC, SKIP           |
| `FILE_RECOVERY`   | `NON_TRANSACTIONAL` | ID 2, `0 0/5 * * * ?`, UTC, SKIP         |
| `SAFE_RETENTION`  | `TRANSACTIONAL`     | ID 3, `0 0 3 * * ?`, UTC, SKIP           |
| `PULSE`           | `TRANSACTIONAL`     | 자동 예약 없음. 앱의 중립 실제 효과 예제 |

`bootstrap-defaults=true`일 때 등록된 작업의 기본 예약을 처음 한 번만 생성한다. 이후 수동 cron 변경·일시정지·revision은 재시작 때 덮어쓰지 않는다. 메시징 OFF로 앞의 두 작업이 등록되지 않았다면 해당 기본 예약을 건너뛴다. 공개 새 예약 ID는 100부터다.

Quartz는 Boot JDBC `LocalDataSourceJobStore`와 앱의 같은 DataSource/JpaTM을 사용한다. 예약 행과 Quartz trigger 변경은 같은 트랜잭션에서 commit/rollback한다. 실행 claim은 별도 트랜잭션으로 저장하고, `TRANSACTIONAL` 작업의 효과와 SUCCESS 이력은 같은 효과 트랜잭션으로 처리한다. 실패 효과를 rollback한 뒤 FAILED 이력과 `JOB_FAILED`를 별도 트랜잭션에 남긴다. 원래 Throwable을 Quartz 로그나 공개 이력으로 전달하지 않는다.

네트워크 작업은 `NOT_SUPPORTED` 경계에서 호출한다. 메시징 claim·확정은 해당 서비스의 별도 트랜잭션이 담당한다. `SAFE_RETENTION`은 등록 작업의 같은 트랜잭션에서 완료 outbox/inbox·브라우저 보존 자료·완료 실행 이력을 batch로 삭제한다. PENDING·DEAD 메시지나 RUNNING 실행을 완료 자료처럼 지우지 않는다.

같은 jobCode는 고정 JobKey이며 dispatcher에 `@DisallowConcurrentExecution`을 적용한다. schedule ID와 원래 예정 시각으로 만든 runKey 중복은 한 이력으로 제한한다. 이는 네트워크 효과까지 Quartz가 정확히 한 번 보장한다는 뜻이 아니다. 현재 H2 단일 프로세스 운영 경계를 분산 lease/HA 보장으로 확대하지 않는다.

## 예약 API

기본 URL은 `/api/operations/jobs`다. 모든 조회·변경은 현재 ADMIN 검사이며, 변경은 기존 CSRF를 적용한다. Reference는 매번 현재 DB 사용자를 다시 읽는다. Starter는 현재 인증 provider를 조회하며 Reference 사용자 업무를 import하지 않는다.

| 메서드·경로                   | 입력                               | 응답 schema·동작                                                          |
| ----------------------------- | ---------------------------------- | ------------------------------------------------------------------------- |
| GET `/registered`             | 없음                               | `OperationalRegisteredJobsResponse`: `items`의 `jobCode`, `executionMode` |
| GET `/schedules`              | `page=0`, `size=20`                | `OperationalSchedulePage`, ID DESC                                        |
| GET `/schedules/{id}`         | ID                                 | `OperationalScheduleResponse`, 없음 404. 직접 URL 선택용                  |
| POST `/schedules`             | `OperationalScheduleInput`         | 새 예약 200, revision 1                                                   |
| PUT `/schedules/{id}`         | `OperationalScheduleUpdateInput`   | revision CAS, jobCode 변경 거절                                           |
| POST `/schedules/{id}/pause`  | `OperationalScheduleRevisionInput` | trigger 해제, enabled false                                               |
| POST `/schedules/{id}/resume` | 같은 입력                          | trigger 재생성, enabled true                                              |
| GET `/runs`                   | `page`, `size`, 선택 `scheduleId`  | `OperationalRunPage`, startedAt DESC·ID DESC                              |

예약 입력은 `jobCode`, `cron`, `timeZone`, `misfirePolicy`, `enabled`다. update에는 `revision`이 추가된다. cron의 초 필드는 정확히 `0`, 최대 120자다. 서버의 실제 ZoneId 목록과 유효한 다음 실행 시각을 검사한다. misfire는 SKIP·FIRE_ONCE만 허용한다. page는 0~1,000,000, size는 1~100이다. stale revision은 409 `REVISION_CONFLICT`, 동일 값 update/pause는 revision을 증가시키지 않는다. 즉시 실행·빠른 초 cron·예약 삭제·실패 임의 재시도 API는 제공하지 않는다.

`OperationalScheduleResponse`는 `id`, `jobCode`, `cron`, `timeZone`, `misfirePolicy`, `enabled`, `revision`, `createdAt`, `updatedAt`, `nextFireAt` 10필드다. 일시정지 상태의 `nextFireAt`은 null이다. `OperationalRunResponse`는 `id`, `scheduleId`, `runKey`, `jobCode`, `scheduledAt`, `startedAt`, `completedAt`, `state`, `reasonCode`, `attempt` 10필드다. state는 RUNNING·SUCCESS·FAILED이며 완료 전 시각과 성공 reason은 null이다. SKIP으로 실행되지 않은 예정 시각을 실행 성공 이력으로 만들지 않는다.

## 브라우저 오류 API와 개인정보 경계

POST `/api/operations/browser-errors`는 인증된 모든 역할과 CSRF를 요구하고, 성공 202 `BrowserErrorAccepted {accepted:true}`를 반환한다. body는 아래 7필드만 받는다.

| 필드            | 서버 검증                                                         |
| --------------- | ----------------------------------------------------------------- |
| `schemaVersion` | 정수 1                                                            |
| `clientEventId` | canonical UUID 문자열                                             |
| `source`        | VUE·WINDOW·REJECTION                                              |
| `eventCode`     | VUE_ERROR·WINDOW_ERROR·UNHANDLED_REJECTION·UNKNOWN_RUNTIME        |
| `appVersion`    | 설정된 앱 버전과 정확히 일치. 설정 자체는 최대 64자의 유효 SemVer |
| `routeCode`     | 앱 프로필의 고정 Router name allowlist                            |
| `componentCode` | ROOT                                                              |

UNKNOWN_RUNTIME 외에는 source/eventCode 조합도 일치해야 한다. 원문 message·stack·URL·query·입력 body 필드를 추가하지 않는다. unknown key·duplicate JSON key·trailing JSON·float schemaVersion·허용하지 않은 코드와 타입은 400이다. JSON 외 content type은 415다. 보안 filter 다음의 bounded body filter가 Content-Length가 없거나 실제 chunked framing인 요청도 제한+1 byte까지만 읽어 4 KiB 초과를 413으로 거절한다.

인증 actor별 20/min, 앱 전체 200/min을 단일 프로세스의 제한된 메모리 bucket으로 검사한다. 초과는 429 `RATE_LIMITED`와 1~60초 `Retry-After`다. 이를 여러 서버를 합친 분산 rate limit으로 표현하지 않는다. 기본 bucket key는 서버가 확인한 subject이며 IP·사용자 입력·오류 원문을 metric label로 쓰지 않는다.

fingerprint는 appVersion/source/eventCode/routeCode/componentCode의 SHA-256이다. 같은 actor subject의 동일 clientEventId는 receipt unique 제약으로 한 번만 집계한다. 다른 fingerprint로 재사용한 ID는 400이다. 서로 다른 동시 이벤트는 group의 atomic UPDATE로 occurrenceCount에 합산한다. coarse code 기반 집계이므로 서로 다른 원문 오류가 같은 group에 속할 수 있다. 원문을 보관해 분류 정밀도를 높이지 않는다.

GET `/groups`와 `/groups/{id}/occurrences`는 현재 ADMIN만 사용할 수 있다. page/size bounds는 예약 조회와 같다. group 필터는 선택 `source`, `eventCode`이며 lastSeenAt DESC·ID DESC다. occurrence는 occurredAt DESC·ID DESC다. occurrence의 6필드는 id/groupId/actorId/actorSubject/requestId/occurredAt이며 Starter actorId는 null이다. 서버 UTC micro·서버 requestId만 저장한다. 허용하지 않은 requestId는 null로 버린다.

기본 보존은 occurrence 30일, receipt 30일, 비활성·발생 자료가 없는 group 90일이며 각 purge는 batch 500으로 제한한다. 현재 설정 값과 보존 여부는 서버 설정의 책임이다. 기능 관측은 원문 없는 `OperationalEvent`의 SCHEDULE_RUN·BROWSER_ERROR_ACCEPTED·BROWSER_ERROR_REJECTED와 고정 Outcome으로 연결한다.

OpenAPI 3.1의 최초 실제 capture에서 schemaVersion이 string으로 생성된 문제를 확인했다. dev 전용 customizer는 `BrowserErrorInput.schemaVersion`만 숫자 IntegerSchema/enum `[1]`/int32/minimum·maximum 1로 교정한다. 생성 TS 수동 수정은 하지 않는다. 실제 Swagger 숫자·enum 검사는 Starter 테스트와 Root의 재캡처로 확인한다.

## 신규 소비 앱의 선택 운영 템플릿

`templates/starter-v2`는 framework 0.3.0용 templateVersion 2이며, 생성기는 framework 0.1.0/0.2.0에 기존 v1을 계속 선택한다. v1 manifest SHA와 파일 내용은 그대로 보존한다. v2는 검토된 자체 소스 82파일만 registry SHA allowlist로 생성하고, Reference 업무 소스·기존 runtime·DB·secret·잠금 파일을 가져오지 않는다.

소비 앱은 Notes V1, audit V2, operations messages V3, Quartz/browser V4를 소유한다. 기본 prod/dev는 운영 기능 OFF이며, 별도의 `operations` 프로필과 private 연결 설정을 선택해야 켜진다. `prepare-operations.mjs`는 새 owned 디렉터리에 필요한 두 secret만 모드600으로 생성하거나 사용자가 지정한 자신의 private 인프라 파일만 복사하고, 기존 파일·symlink를 거절한다. 값은 출력하지 않는다. 일반 Notes API 타입은 소비 앱의 actual generated/api를 사용하고 운영 기술 API 타입은 공개 `@sc/runtime`의 `ApiComponents`를 사용한다.

앱 버전은 framework 0.3.0과 별개인 1.0.0이다. 브라우저 collector와 서버 app-version을 동일하게 설정하고, 실제 Router name인 notes/patterns/운영 세 화면을 허용한다. 운영 미활성 상태에서는 collector를 설치하지 않는다. 상세 실행 순서·인프라 준비·동적 vendor settings·개인 파일 경계는 v2 README/AGENTS에서 설명한다.

첫 정적 검증은 [50검사 PASS 결과](../검증/012-generator-v2-static-first.json)다. 생성기와 v2 소스의 scoped ESLint/Prettier, XML 3파일·shell 6파일 문법 검사도 통과했다. 결과의 `actualArtifacts`, `actualGeneration`, `mavenExecuted`, `browserExecuted`는 모두 false다. v2 JUnit 10개는 작성만 완료했으며 실제 framework 0.3.0 배포 세트의 cold consumer 설치·생성·Maven·JAR·운영 UI 검증은 별도 실행 대기다. 이 정적 결과로 신규 소비 앱의 실행 완료를 표시하지 않는다.
