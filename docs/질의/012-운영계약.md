# 012 현재 운영 구현 계약

현재001~012 구현·로컬 검증을 완료했다. 실제 최신 결과와 후속 AI 질의는 [012 완료 기록](012-운영모듈완료.md)과 [최종 집계](../검증/012-final-summary.json)를 따른다.

이 문서는 구현된 0.3.0 소스와 실제 로컬 검증을 기준으로 한다. 아래 접힌 **구현 전 제안**은 당시 기록으로 보존한다. 현재 실행 설정은 `backend/*-app/src/main/resources/application-operations.yml`, 공개 SPI는 core, 중립 구현은 autoconfigure, 업무 controller·DDL은 각 앱이 소유한다. Redis/JWT/SSO는 제외한다.

## 현재 실행 경계

| 영역          | 기본     | 실제 구현·검증                                                                                       |
| ------------- | -------- | ---------------------------------------------------------------------------------------------------- |
| RabbitMQ      | OFF      | H2 outbox/inbox, confirm+mandatory return, manual ACK, 재시도/DLQ, 두 crash 경계 실제 broker 검증    |
| Quartz        | OFF      | Boot JDBC 동일 DS/TM, 등록 작업4종, 기본 예약3개, UTC/ZoneId·misfire·revision·비중첩·실제 PULSE 효과 |
| 브라우저 오류 | OFF      | 인증/CSRF, 제한된7필드, chunked413/429, receipt 중복 방지, H2 fingerprint/이력과 ADMIN 화면          |
| 관측          | OFF      | private observer 인증, bounded metrics/logs, Feign trace, 실제 Prometheus/Tempo/Loki/Grafana 조회    |
| 파일·감사     | 옵션     | 업무 TX의 durable outbox와 실제 파일 삭제/감사 handler, 이전-run journal 회수                        |
| 백업/복원     | 명시 CLI | 앱 정지·Java/Python 배타 lock, H2+blob SHA 세트, 새 root·동일 JAR 복원/hostile input 거절            |

인증된 GET `/api/framework/capabilities`는 네 가지 실제 기능 상태를 반환한다. 운영 관리 API는 ADMIN, 보고 POST는 로그인 사용자와 CSRF가 필요하다. 버튼 숨김은 서버 권한 검사를 대신하지 않는다. `dev`는 Swagger를 제공하고 `prod`는 Swagger를 제공하지 않는다.

## 설정과 공개 부품

`ScMessage`/`DurableMessagePublisher`/`MessageHandler`, `RecoverableFileStorage`/`FileReferenceLookup`, `RegisteredOperationalTask`/`ScheduledRunContext`, `OperationalEvent`/`OperationalEventSink`를 사용한다. 모든 메시지 type·jobCode는 앱에서 미리 등록하며 임의 class·SQL·외부 요청 payload 실행을 받지 않는다.

메시지 설정 키는 **flat** `sc.framework.messaging.publish-max-attempts=5`, `confirm-timeout=5s`, `lease=30s`, `poll-interval=1s`, `batch-size=20`, `delivery-limit=4`, `prefetch=10`, `retry-min=1s`, `retry-max=30s`, `retention-days=30`이다. 아래 과거 제안의 `publish.*`/`consumer.*` 계층을 실행 설정으로 사용하지 않는다. `application-id`는 고정한 3~48자 소문자 namespace이며 환경변수는 Spring의 canonical **SC_FRAMEWORK_MESSAGING_APPLICATIONID**이다.

예약은 등록 작업 OUTBOX_DISPATCH/FILE_RECOVERY/SAFE_RETENTION/PULSE만 사용한다. 기본 설정은 자동 예약을 만들지 않으며 operations profile에서 bootstrap-defaults=true로 앞의 세 작업만 최초 생성한다. 작업 종류당 예약 하나(job_code UNIQUE)를 관리하고 이미 수정·중지한 설정을 재시작 시 덮어쓰지 않는다. cron은 초0의 Quartz6/7필드, 실제 ZoneId, SKIP/FIRE_ONCE와 revision을 검증한다.

오류 보고는 schemaVersion=1(integer), clientEventId(UUID), source/eventCode allowlist, 소비 앱의 appVersion, 등록 routeCode/componentCode만 받는다. Reference/내장 Starter는0.1.0, 생성 앱은1.0.0이다. message/stack/URL/query/form/cookie/token은 수집하지 않는다. 공통 collector는 앱 버전을 명시 옵션으로 받는다. 전체 raw application.log를 Loki로 전송하지 않는다.

## 데이터와 사용 순서

Reference 운영 migration V6/V7, 내장 Starter V2/V3(audit V1), 생성 v2 운영 V3/V4(Notes V1/audit V2)는 앱이 소유한다. H2 DDL 커밋을 DML rollback으로 설명하지 않는다. 메시지 효과+inbox+COMPLETED는 같은 transaction이고 ACK는 commit 후 보낸다. 네트워크 publish는 DB TX 밖이다. 중복 발생을 허용하는 at-least-once 모델이며 외부 부작용까지 exactly-once라고 보장하지 않는다.

1. [실행 문서](../operations.md)의 새 private 운영 root를 만들고 prepare-operations.py로600 secret을 준비한다.
2. digest 고정 compose.operations.yaml로6개 인프라를 실행한다. native 앱은 dev,operations, Docker 앱은 prod,operations로 실행한다.
3. [API 문서](../api.md)의 운영 관리 화면·권한·URL과 ON/OFF Swagger snapshot을 확인한다.
4. 백업은 앱을 정지한 뒤 backup-runtime.py, 복원은 동일 JAR·새 빈 root에서 restore-runtime.py를 실행한다. secret은 백업에서 제외하며 별도로 준비한다.
5. 운영 DDL을 적용한 DB의0.2 제자리 downgrade는 지원하지 않는다. 011의 동일-DDL rollback 성적을012에 확대 적용하지 않는다.

# 012 운영 계약

이 문서는 2026-10-07의 소스와 공식 자료를 읽어 정한 **구현 전 계약**이다. 011의 최종 검증·마감과 별개로 012 준비만 기록하며, 아래 API·SPI·schema·파일명은 구현을 위한 제안이다. 실제 main 코드·의존성 설치·migration·운영 서버 실행을 완료한 문서가 아니다. Redis·JWT·SSO는 제외한다. RabbitMQ·Quartz·관측·브라우저 오류·백업은 모두 구현 대상이며 소비 앱의 활성 옵션과 구현·검증 완료를 구분한다.

## H2 outbox/inbox schema

H2 DDL은 소비 앱 Flyway가 소유한다. 공통이 자동 생성하지 않는다. Reference의 `V6__operations_messages.sql`을 메시지 단계에, `V7__operations_scheduler_browser.sql`을 Quartz·브라우저 단계에 예약한다. 기존 V1~V5의 bytes/checksum을 바꾸지 않는다.

| table/column                                 | 제약·의미                                                     |
| -------------------------------------------- | ------------------------------------------------------------- |
| `sc_message_outbox.event_id`                 | UUID PK, 재발행·복원에도 동일                                 |
| `type`, `schema_version`                     | 등록 type 최대64자, version=1                                 |
| `payload`, `payload_sha256`                  | JSON 최대16KiB, SHA256 64 hex; 원문은 공개 운영 조회에서 제외 |
| `state`                                      | PENDING/CLAIMED/PUBLISHED/COMPLETED/DEAD allowlist            |
| `dispatch_attempts`, `next_attempt_at`       | 유한 publish 시도와 UTC due time                              |
| `lease_token`, `lease_until`                 | claim UUID·UTC 만료, update의 비교 조건                       |
| `last_failure_code`                          | 최대32자 fixed code; Throwable message/URL/body 저장 금지     |
| `created_at`, `published_at`, `completed_at` | UTC TIMESTAMP(6) WITH TIME ZONE; 후자 둘 nullable             |

| `processed_at`, `payload_sha256`             | side effect와 함께 commit한 시각·내용 식별                    |

outbox의 `(state,next_attempt_at)`·`lease_until`·`created_at` index를 둔다. 같은 eventId로 다른 내용이 들어오면 거절한다. Actor ID/requestId는 message 목적에 필요한 audit DTO 범위에만 있고 metric label에는 사용하지 않는다.

Starter operations profile은 기존 audit migration의 V1과 메시지 V2·예약/브라우저 V3을 함께 읽는 구성을 제안한다. audit profile이 이미 적용된 H2의 upgrade와 신규 H2를 모두 확인한다. 별도 디렉터리라는 이유로 같은 Flyway locations에 V1을 두 개 두지 않는다. 앱 활성 설정 파일은 Root가 확정한다.

## 발행·소비·재시도

1. 업무 write와 outbox INSERT가 같은 transaction에서 commit한다. rollback이면 성공 event도 없다.
2. dispatcher가 짧은 별도 TX로 due row를 CAS claim하고 lease/attempt를 저장한다. publish와 confirm wait는 DB TX 밖에서 수행한다.
3. persistent JSON을 durable exchange/queue에 `mandatory=true`로 발행한다. confirm ACK만으로 충분하지 않고 return 없음도 확인한 후 lease token 조건으로 PUBLISHED를 기록한다. NACK·return·timeout은 고정 code와 유한 backoff, 마지막 publish 실패는 DEAD다.
4. consumer는 payload/type/schema/hash를 검증한다. 매 실제 시도마다 DB TX에서 inbox unique INSERT·등록 handler 효과·outbox COMPLETED를 함께 commit한 뒤 같은 channel에서 manual ACK한다.
5. 이미 commit한 inbox가 있으면 같은 효과를 반복하지 않고 ACK한다. 처리 실패는 TX rollback 뒤 `basicReject(tag,true)`로 재시도한다. invalid payload는 `basicReject(tag,false)`로 DLQ에 보낸다.
6. terminal 실패·broker DLQ는 고정 reason만 H2 DEAD에 반영한다. DB 장애 동안 terminal 기록이 실패할 수 있으므로 DLQ observer가 복구 후 known event의 DEAD 상태를 저장하는 경계를 포함한다. 임의 메시지 원문을 로그나 DTO로 출력하지 않는다.

consumer가 매우 빨라 dispatcher의 confirm 처리 전에 COMPLETED로 바뀔 수 있다. dispatcher의 후속 update가 해당 상태를 PUBLISHED/PENDING으로 덮지 않도록 lease+현재 상태 CAS를 검사한다. broker confirm 후 DB update 전 crash, handler commit 후 ACK 전 crash를 각각 검사한다. 두 경우 같은 UUID가 다시 전달돼도 committed side effect는 한 번이다.

RabbitMQ 4.3에서는 nack requeue가 failure delivery count를 증가시키지 않는다. `reject`와 실패 횟수 제한을 연결해야 무한 반환 loop를 막는다. quorum queue의 native delayed retry를 사용하며 source와 DLQ는 durable로 구성한다. DLX `at-least-once`·`overflow=reject-publish`·bounded queue size를 함께 지정한다. 단일 로컬 broker의 durable quorum queue 실행은 다중 노드 HA 검증으로 확대하지 않는다. [confirm/ACK 공식 경계](https://www.rabbitmq.com/docs/confirms), [quorum retry·DLX 공식 설정](https://www.rabbitmq.com/docs/quorum-queues).

## 감사 저장과 HTTP 결과

durable 감사 publisher는 기존 `SecurityAuditEvent`의 bounded identity/action/outcome/resource/requestId/reasonCode만 codec으로 보낸다. 비밀번호·hash·session·token·request body·exception 원문을 새 필드로 넣지 않는다.

business SUCCESS는 원래 write와 같은 TX에 outbox를 넣는다. audit queue INSERT 자체가 실패하면 commit 전에 write도 rollback하는 경계다. 이 선택은 과거 afterCommit best-effort와 구분한다. commit된 HTTP의 결과를 바꾸는 sink 호출은 하지 않는다. worker의 sink 실패는 retry/DLQ/운영 counter로 처리한다. 기본 Jdbc sink는 inbox와 같은 TM/DS로 실제 audit row를 저장한다.

로그인/CSRF/401/403 등 non-TX 감사는 별도 TX로 enqueue하고 기존 안전한 HTTP 결과를 유지한다. DB 자체가 불가능한 경우 감사 event의 무손실을 주장하지 않고 고정 counter/진단을 남긴다. custom publisher/sink backoff를 유지하며, 외부 시스템에 쓰는 custom sink의 exactly-once는 adapter의 책임을 별도로 확인해야 한다.

## 파일 write journal·정리

UUID blob이 DB에 없다는 이유만으로 sweep하면 아직 commit하지 않은 정상 업로드를 지울 수 있다. local recoverable adapter는 bytes를 쓰기 전에 `.pending/<UUID>.json`에 run UUID/createdAt만 원자 기록한다. bytes는 `.part/<UUID>`에 쓰고 완료 후 원래 UUID 파일로 atomic move한다. 기존 10MiB 한도·실제 PNG/JPEG/PDF 확인·EXIF 좌표 계약·opaque key·symlink 거절을 유지한다.

같은 uploads root는 단일 프로세스가 배타 FileLock으로 소유한다. 현재 run의 활성 write는 복구 대상에서 제외한다. metadata commit 뒤 journal을 제거하고 discard/rollback은 idempotent cleanup한다. 이전 run의 marker만 startup 복구에서 reference lookup과 대조한다. DB reference가 있으면 원본 blob을 보존하고 marker만 해제하며, reference가 없으면 FILE_DELETE 작업을 영속 기록한다. 내부 marker·UUID 규칙 밖 자료나 다른 root를 지우지 않는다.

durable mode의 `afterCommitDelete(key)`는 이름/호출 호환을 유지하면서 호출 당시 business TX에 FILE_DELETE outbox를 적재한다. 물리 삭제는 commit 후 worker가 한다. rollback 정리는 REQUIRES_NEW 기록 또는 기존 journal의 다음 startup 회수로 복구 가능해야 한다. 이미 없는 blob의 delete는 성공이다. 실패는 유한 retry/DEAD로 남기며 metadata commit 이후 I/O 오류로 HTTP를 500으로 바꾸지 않는다.

write 전/후·metadata commit 전/후·physical delete 후 inbox commit 전 지점을 실제 중단해 orphan 회수·referenced blob 보존·반복 삭제를 검사한다. journal·lock의 native 동작을 작성만으로 보장했다고 표시하지 않는다.

## 일관 backup/restore

백업은 앱을 정상 정지하고 배타 runtime maintenance lock을 획득한 상태에서만 만든다. H2 DB 전체·UUID uploads 원본·pending journal을 동일 세트로 복사한다. 앱도 같은 lock을 사용해 백업 중 새 기동/변경을 거절해야 한다. H2 `BACKUP`만 수행하여 uploads의 일관성까지 보장한다고 설명하지 않는다. [H2 공식 shutdown/backup](https://h2database.com/html/commands.html#backup).

| 경계        | 계약                                                                                                                          |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------- |
| source      | 명시한 자기 runtime만, 실행 중·symlink·원본 WorkboardVue runtime 거절                                                         |
| destination | 새 private root만, directories0700/files0600, 기존 backup/restore target 덮어쓰기 금지                                        |
| manifest    | format1/app/framework/H2/build/schema(Flyway versions+checksums), UTC, 상대 path/size/SHA256·세트 digest                      |
| 제외        | plaintext bootstrap secret·로그·브라우저 자료·외부 broker/관측 volume. DB의 기존 user hash는 DB 안에 유지되지만 출력하지 않음 |
| restore     | 모든 hash/path/schema/build 호환 확인 후 새 staging에 배치→atomic rename. 변조/미래 schema/기존 target은 안전한 code로 거절   |
| 검사        | 별도 SC_HOME fresh JAR의 사용자/권한/요구사항/revision/annotation/image/PDF/audit/예약 유지, bytes 일치                       |

Java NIO FileLock과 Python `fcntl.lockf`가 실제 macOS/Linux에서 같은 byte range를 상호 거절하는지 검사한다. Python `flock`을 같은 구현이라고 가정하지 않는다. OS가 다른 경로의 미검증을 숨기지 않는다. restore할 JAR/H2/schema의 허용 관계를 manifest에서 검사하며, 자동 migration으로 future schema를 임의 downgrade하지 않는다.

broker volume 자체를 복원하지 않아도 H2가 메시지 원본이어야 한다. restore 후 COMPLETED/inbox는 유지하고 inbox 없는 PUBLISHED·만료 CLAIMED만 같은 UUID로 PENDING 재개한다. DEAD를 자동 replay하지 않는다. 새로운 Rabbit queue에서 미완료 처리 한 번·완료 감사 중복0·file delete 반복 안전성을 확인한다. 완료 outbox와 inbox는 함께 retention 처리하고, 미완료 payload를 제거하여 broker 복원 가능성을 잃지 않는다.
