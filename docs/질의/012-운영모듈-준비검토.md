# 012 운영 모듈 준비 검토

2026-10-07 현재 소스·실제 JAR·로컬 Docker CLI와 공식 자료를 읽어 작성한 준비 문서다. 001~009는 기존 로컬 완료 기록을 유지하며 010은 통합 검증 중이다. 011 패키징과 012 운영 기능을 완료한 문서가 아니다. 이번 검토는 설치·새 main 구현·기존 컨테이너 변경·Docker Desktop UI 조작을 수행하지 않았다. Redis/JWT/SSO는 계속 제외하며 조건부 운영 기술도 전부 구현한다. 소비 앱의 활성 옵션과 구현 완료 여부를 구분한다.

## 현재 구성에서 고칠 구체적 부분

`compose.yaml`은 Reference 하나와 `/app/data` volume만 정의한다. 010부터 파일 metadata가 H2에 들어가므로 DB만 유지하고 uploads를 잃으면 파일 읽기가 깨진다. `scripts/docker-entrypoint.sh`는 `/app/data`·`/app/logs`만 만들고 uid 10001로 전환한다. 현재 Reference의 기본 uploads 상대 경로는 이 사용자에게 쓰기 가능하도록 준비되지 않았다. 012에서는 `SC_UPLOAD_DIR=/app/uploads`, 명시적 uploads/logs volume과 owner를 구성하고 실제 새 이미지 쓰기·다운로드·컨테이너 재생성으로 확인한다. 현재 Docker 실행 성공을 소급해서 주장하지 않는다.

현재 Dockerfile의 base tag는 버전/계열을 표시하지만 immutable digest를 고정하지 않는다. 012 실행 환경에 맞는 official multi-arch image와 digest를 검증하여 pin한다. Compose secret는 image/환경변수에 비밀번호 값을 넣지 않고 기존 private file/tmpfs 복사 방식을 유지한다. [Compose secret 사용](https://docs.docker.com/compose/how-tos/use-secrets/).

## 순차 구현과 실제 완료 조건

1. 운영 public SPI/DTO와 optional 활성 설정을 정하고 두 소비 앱의 자기 migration을 작성한다. 공통은 Reference를 import하거나 소비 앱 DDL을 자동 생성하지 않는다. 앱 기본 비활성에서는 MQ/관측 서버에 연결하지 않는다.
2. RabbitMQ 생산/소비를 구현한다. 업무 transaction의 H2 outbox, broker confirm 이후 published 갱신, consumer의 unique inbox+업무 commit 이후 ACK를 연결한다. confirm/commit 사이 중단으로 재전달된 동일 event는 업무에 한 번 반영되어야 한다. finite retry/backoff·DLQ·broker 중단/재기동을 실제 검사한다. 임의 JPA 객체·비밀번호·본문을 메시지에 넣지 않는다.
3. Quartz JDBC JobStore를 구현한다. Flyway가 schema를 소유하고 `initialize-schema=never`를 유지한다. 등록된 job ID/제한된 입력만 실행하며 Java 직렬화 payload 대신 제한된 문자열 값을 쓴다. 예약/시간대/UTC 이력·재기동 유지·misfire·실패·중복 실행 방지를 실제 H2/앱 재기동으로 검사한다.
4. Micrometer Prometheus registry와 HTTP/JVM/Hikari/업무/outbox/cleanup 지표를 구현한다. 사용자 ID·요청 본문·임의 URL을 metric label에 넣지 않는다. 전용 management 접근/내부 network scrape 계약을 정하고 일반 API 세션/CSRF와 ADMIN 경계를 유지한다. 실제 scrape로 값 증가·권한 거절을 검사한다.
5. Tracing bridge/exporter와 Feign observation을 붙인다. 현재 requestId를 대체하지 않고 traceId/spanId를 추가한다. 실제 앱→loopback 외부 mock span/parent 연결, timeout/error, Collector→Tempo 조회와 로그 correlation을 검사한다. 외부 Cookie/Authorization/CSRF 전달 금지와 no-retry 계약도 다시 검사한다.
6. Collector Contrib의 OTLP receiver는 Compose 내부에서 접근 가능하도록 endpoint를 명시하며 호스트 공개는 loopback 또는 내부 network로 제한한다. traces는 Tempo, 정제된 structured logs는 Loki의 native OTLP HTTP(`/otlp`)로 보낸다. 현재 라이브러리의 민감 SQL/exception 원문 로그를 그대로 중앙 수집하지 않는다. 별도의 allowlist 운영 event 파일·redaction을 두고 실제 canary가 Loki/Tempo/Grafana에 없는지 확인한다.
7. Vue error handler/window error/unhandled rejection 수집을 구현한다. app/version/route template/error code·제한된 frame 등 공개 DTO만 받고 쿠키·토큰·query·폼 입력·원문 body를 제외한다. 서버에서 다시 검증·redaction·요청 크기/rate 제한·fingerprint 집계·retention을 적용한다. ADMIN 이력 UI·중복 집계·세션/CSRF·거절/실패와 Loki 연결을 실제 browser/HTTP로 확인한다.
8. Grafana OSS의 datasource/dashboard를 provision한다. 실제 지표·log·trace 결과와 UI 상태를 검사하고 원격 계정/API를 사용하지 않는다. Tempo 3.x는 monolithic mode에서 Kafka 없이 실행할 수 있지만 distributed mode는 Kafka-compatible buffering을 요구한다. 이 로컬 기준에서는 monolithic mode를 사용한다. Grafana 내부 metadata 저장소는 앱 H2와 별개다.
9. 010의 physical file 삭제와 감사 보존을 crash-safe 운영 작업으로 보강한다. DB commit과 같은 transaction에 영속 작업을 기록하고 idempotent worker·finite retry·ADMIN 상태·운영 지표를 제공한다. 현재 afterCommit callback/counter를 영속 queue와 동일하게 설명하지 않는다.
10. 자기 임시 runtime의 H2+uploads 백업/복원을 구현한다. 정지 상태 또는 명시적인 일관성 경계에서 DB와 파일을 같은 세트로 만들고 버전/해시/schema manifest를 검사한다. DB의 `BACKUP`만 수행해서 업로드 일관성까지 보장한다고 하지 않는다. 별도 root로 복원한 fresh JAR에서 사용자/요구사항/revision/화면/첨부/감사·실제 원본 bytes를 재확인한다. 원본 WorkboardVue DB/uploads/secret를 사용하지 않는다. [H2 backup 명령](https://h2database.com/html/commands.html#backup).

## 범위와 남은 실행

Redis cache/ring·JWT·SSO·상용 관측 기능은 넣지 않는다. 단일 로컬 Loki/Tempo의 memory ring·filesystem은 다중 노드 운영 보장으로 확대하지 않는다. RabbitMQ와 Quartz는 서로 다른 전달/예약 책임을 가지며 각 실패 경로를 검사한다. Grafana의 표시만 확인하고 H2 inbox·실제 ACK·영속 예약·파일 복원을 완료로 표시하지 않는다.

- [ ] AMQP/Quartz/Prometheus/Tracing 의존성 실제 BOM 설치·compile/runtime
- [ ] MQ 중복/ACK/confirm/retry/DLQ·중단/재기동
- [ ] Quartz 예약/시간대/misfire·영속 재기동·중복 실행
- [ ] 지표 scrape·Feign trace parent·Collector/Tempo/Loki 실제 저장/조회
- [ ] 브라우저 오류/H2 fingerprint/redaction/rate/retention·ADMIN UI
- [ ] Grafana datasource/dashboard 실제 표시·민감 canary 부재
- [ ] DB+uploads 원자적 세트/manifest 검사·새 root 복원·파일 bytes
- [ ] Docker daemon 사용 가능 상태에서 실제 전체 Compose lifecycle
- [ ] 011 배포 산출물·012 전체 회귀 및 새 실행 로그/잔여 제한

이 준비 문서의 작성/형식 확인은 위 기능 실행을 대신하지 않는다. 원격 CI·Linux 시각 기준·VoiceOver 실제 음성·수동 axe incomplete 검토는 기존 미확인 상태를 유지한다.
