# ScFramework 레거시 마이그레이션과 상용 프레임워크 적합성 검토

2026-10-09 기준. 제품 목적은 고객의 레거시 내부 시스템을 이관하고 이후 업무 개발에 반복 사용하도록 판매하는 공통 프레임워크다. 대상은 업무 로직이 JSP에 혼재한 순수 JSP, EJB, 구형 Spring 시스템이며, 현재 업무 앱은 제품을 검증하는 레퍼런스다.

현재 구조는 공통 UI와 실행 기반을 독립 패키지로 제공하는 데 적합하다. 세션 격리, CSRF, 오류 처리, 트랜잭션, 공개 패키지 경계에도 실질적인 구현이 있다. 다만 레거시 이관에 필요한 DB·인증·트랜잭션 어댑터와 개발 절차가 제품화되지 않았고, 반복 업무 개발을 줄이는 기능 일부가 레퍼런스 앱에 남아 있다. 따라서 현재 상태는 **재사용 가능한 기반과 업무 예제를 갖춘 프레임워크 후보**이며, 다양한 고객의 JSP/EJB 시스템을 낮은 비용으로 이관할 수 있는 완성된 제품으로 판정하기에는 보완이 필요하다.

실제 고객 코드·DB·EJB 설정은 제공되지 않았다. 아래의 코드 결함과 설계 사실은 현재 저장소 기준이며, 고객 환경에 따라 발생하는 위험은 조건을 명시했다. 구현 불가능과 현재 제공되지 않음을 구분한다. Redis·JWT·SSO 제외와 서버 세션·CSRF 유지라는 기존 방침은 그대로 적용한다.

**유지할 설계**

- `apps`가 `packages`를 소비하고 공통 패키지가 업무 앱을 참조하지 않는 방향은 고객 앱별 독립 유지보수에 맞다. 빌드된 JS·타입·CSS와 Maven 라이브러리를 제공하고 소스 복사를 요구하지 않는 방식도 유지한다.
- [runtime](../../frontend/packages/runtime/src/runtime.ts)은 앱마다 Router·Pinia·QueryClient를 생성하고 세션 전환 시 캐시와 진행 중 요청을 정리한다. [HTTP client](../../frontend/packages/runtime/src/http.ts)는 CSRF·401·필드 오류·다운로드 오류를 일관되게 처리한다.
- [Security 자동 설정](../../backend/framework-autoconfigure/src/main/java/dev/scframework/autoconfigure/ScSecurityAutoConfiguration.java)은 소비 앱의 인증 구현과 SecurityFilterChain 교체를 허용한다. 이번 2개 테스트에서 교체와 인증 어댑터 누락 시 시작 거절을 확인했다.
- [Querydsl 자동 설정](../../backend/framework-autoconfigure/src/main/java/dev/scframework/autoconfigure/ScQuerydslAutoConfiguration.java)은 단일 EntityManagerFactory를 기본으로 삼고 소비 앱의 factory를 존중한다. 복수 DB에서는 명시적 선택을 요구하는 테스트도 있다. 복수 DB가 불가능하다는 의미는 아니다.
- 업무 Service가 최종 권한과 revision을 검사하고, JPA flush와 MyBatis 조회를 같은 트랜잭션에서 사용하는 예제가 있다. UI에서 버튼을 숨기는 것만으로 권한을 처리하지 않는다.
- 공통 표의 자체 계약, 입력 props/emit, Storybook, 날짜의 달력 날짜와 UTC 구분, 엑셀의 행·파일 제한은 반복 업무 개발에 유용하다.
- 생성기의 덮어쓰기 거절·artifact 해시 확인과 독립 소비 앱 검증은 제품 배포에 필요한 기반이다. 이 장점을 유지하면서 이관용 선택지를 추가하는 편이 적절하다.

**도입 전에 해결하거나 범위를 확정할 항목**

1. **공통 서버에도 특정 DB에 의존하는 구현이 있다. 중요도 높음, 코드 확인.** [JdbcMessageStore](../../backend/framework-autoconfigure/src/main/java/dev/scframework/autoconfigure/messaging/JdbcMessageStore.java)는 `LIMIT ?`, [BrowserErrorService](../../backend/framework-autoconfigure/src/main/java/dev/scframework/autoconfigure/browsererrors/BrowserErrorService.java)와 [OperationalSchedulerService](../../backend/framework-autoconfigure/src/main/java/dev/scframework/autoconfigure/scheduling/OperationalSchedulerService.java)는 `LIMIT ? OFFSET ?`를 직접 사용한다. 생성 앱의 Quartz DDL도 H2용이다. Oracle·SQL Server를 대상으로 할 경우 JDBC URL과 드라이버만 바꾸는 것으로 지원이 끝나지 않는다. Oracle과 SQL Server의 공식 행 제한 구문은 각각 [Oracle SELECT](https://docs.oracle.com/en/database/oracle/oracle-database/21/sqlrf/SELECT.html), [SQL Server ORDER BY](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-order-by-clause-transact-sql?view=sql-server-ver17)에 명시되어 있다. DB별 저장소 구현·DDL·페이징·키 생성·시간 타입을 분리하고, 우선 고객 DB 하나에 전체 공통 기능의 계약 테스트를 통과시켜야 한다.

2. **SQL 문법뿐 아니라 오류 이후 트랜잭션 처리도 H2에 기대고 있다. 중요도 높음, 조건부 위험.** `BrowserErrorService.accept()`는 중복 키 예외를 잡은 뒤 같은 트랜잭션에서 다음 SQL을 실행하며 H2 동작을 주석에 명시한다. PostgreSQL은 오류로 중단된 트랜잭션을 단순 Java catch로 복구하지 못하므로 이 경로를 그대로 사용할 수 없다. [PostgreSQL 트랜잭션 문서](https://www.postgresql.org/docs/18/tutorial-transactions.html)는 이때 rollback 또는 savepoint 복구가 필요함을 설명한다. DB별 upsert나 적절한 충돌 처리 전략을 제공하고 동시 요청까지 시험해야 한다. 실제 PostgreSQL 실행에서 재현한 결과는 아니다.

3. **기존 JSP·구형 Spring·EJB 라이브러리의 직접 이식 경로가 없다. 중요도 높음, 이관 설계 필요.** 현재 [서버 parent](../../backend/pom.xml)는 JDK 21·Boot 3 계열이고 Servlet/JPA 코드는 Jakarta API를 사용한다. 기존 Java EE `javax.servlet`, `javax.persistence` 라이브러리와 그대로 호환된다고 볼 수 없다. Java SE에 남아 있는 `javax.sql` 등까지 일괄 변경해서는 안 된다. Boot 3의 Jakarta 전환과 의존성 점검은 [공식 이관 가이드](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-3.0-Migration-Guide)에 설명되어 있다. 구형 WAS를 별도 프로세스로 유지하면서 서버 어댑터로 연결하는 경로와, 서비스 로직을 새 앱에 이식하는 경로를 따로 제공해야 한다.

4. **EJB 트랜잭션을 현재 예제로 치환하면 업무 의미가 달라질 수 있다. 중요도 높음, 조건부 위험.** [NoteService](../../templates/starter-v2/backend/src/main/java/__JAVA_PATH__/notes/NoteService.java)의 예제는 같은 DB의 JPA·Querydsl·MyBatis를 다룬다. EJB CMT, JTA/XA, 복수 DB와 메시징의 원자성, 원격 EJB, stateful bean과 timer 이관 예제는 확인되지 않았다. Spring이 JTA를 지원하지 않는다는 뜻은 아니다. [Spring 트랜잭션 전략](https://docs.spring.io/spring-framework/reference/data-access/transaction/strategies.html)은 별도의 JTA manager와 자원 참여 구성을 설명한다. 기존 트랜잭션을 옛 서버에 남길지, 새 서버로 한 단위씩 옮길지 먼저 정해야 한다. Feign HTTP 호출과 로컬 `@Transactional`만으로 원격 커밋까지 함께 rollback되지는 않는다. 현재 outbox도 기존 XA 의미를 자동 대체하지 않는다.

5. **레거시 URL을 붙일 때 기본 보안 범위를 벗어날 수 있다. 중요도 높음, 조건부 위험.** 기본 SecurityFilterChain은 `/api/**`를 인증 대상으로 하고 나머지는 `anyRequest().permitAll()`이다. 현재 SPA의 정적 리소스와 화면 제공에는 의도가 있지만, 같은 앱에 `/legacy/export.do` 같은 업무 Controller를 추가하고 별도 권한 검사를 하지 않으면 그 요청은 기본 URL 인증 규칙으로 보호되지 않는다. 현재 그런 업무 endpoint가 노출됐다는 판정은 아니다. 이관 템플릿에는 레거시 경로를 명시한 보안 설정과 미인증·무권한 음성 테스트를 포함해야 한다. 소비 앱이 체인을 교체할 때 CSRF·401 JSON·로그아웃 계약도 보존해야 한다.

6. **기존 계정·세션 연결을 개발자가 개별 구현해야 한다. 중요도 높음, 제품 기능 부족.** 서버 `UserDetailsService`와 프런트 `decodeIdentity` 확장점은 좋은 출발점이다. 그러나 [생성 앱 인증](../../templates/starter-v2/backend/src/main/java/__JAVA_PATH__/AppAuthentication.java)은 파일 기반 계정이며 공통 client의 `/auth/login`, `/auth/logout`, `/auth/csrf`, runtime의 `/auth/me` 계약은 고정되어 있다. 기존 사용자 테이블·암호 검증·사번·조직·복수 권한과의 연결 레시피가 필요하다. 같은 쿠키 이름을 사용한다고 구형 서버와 새 서버의 로그인 상태가 자동 공유되지는 않는다. 별도 세션을 쓸 경우 이름·경로를 분리하고, 기존 세션 연결이 필요하면 신뢰 경계와 재인증 정책을 명시한 서버 어댑터를 제공한다. 사용자명만 전달받아 신뢰하거나 기존 세션 객체를 무검증 복사하는 방식은 피한다. Redis·JWT·SSO 도입을 전제로 하지 않는다.

7. **기존 DB 구조와 식별자를 유지하는 경로가 약하다. 중요도 높음, 고객별 확인 필요.** 생성 앱 Notes는 신규 IDENTITY 키·revision·owner를 가진 테이블을 생성하며, Reference 사용자 ID와 Notes 경로는 안전한 양의 JS 정수를 기대한다. 사번 같은 문자열 키, 복합 키, 큰 정수 ID, 기존 sequence·trigger·stored procedure는 별도 매핑이 필요하다. 현재 safe-integer 검사는 무리한 정수 수용을 막는 좋은 방어지만 큰 기존 키를 지원하는 기능은 아니다. ID와 고정 소수점 금액을 문자열로 전달할지, 날짜가 날짜 자체인지 시각인지, null·빈 문자열·한글 인코딩을 어떻게 변환할지 이관 계약에 명시한다. 원본 키를 임의 재발급하면 연관·감사·첨부 연결도 깨질 수 있다.

8. **신구 시스템이 같은 행을 수정할 때 revision 보호만 믿을 수 없다. 중요도 높음, 조건부 위험.** 새 코드가 revision을 검사해도 구형 JSP/EJB 갱신이 같은 revision을 올리지 않으면 그 변경을 잡지 못할 수 있다. 기능·데이터별 쓰기 주체를 하나로 정하고 단계적으로 이관하는 방식이 우선이다. 불가피한 동시 쓰기는 기존 갱신까지 포함한 잠금·변경 감지 계약을 검증한다. 기존 schema에 Flyway를 적용하기 전에 baseline과 변경 권한을 확정하고, 자동 schema 생성이나 운영 DB를 통한 테스트로 대체하지 않는다.

9. **하위 경로 배포와 레거시 URL 병행을 설정 하나로 처리할 수 없다. 중요도 중간, 코드 확인.** runtime은 `history`와 `baseURL`을 받을 수 있으므로 확장은 가능하다. 다만 생성 앱은 기본 `createWebHistory()`·`/api`를 사용하고 Vite `base` 통합 설정이 없다. `/erp` context path만 서버에 추가하는 것으로 브라우저 자산·API·라우트가 모두 맞춰지지는 않는다. [SpaRoutes](../../templates/starter-v2/backend/src/main/java/__JAVA_PATH__/SpaRoutes.java)도 명시 목록이므로 새 화면은 클라이언트 이동뿐 아니라 JAR 직접 URL·새로고침까지 연결해야 한다. `/`, `/erp/`, reverse proxy, 기존 `.do` URL, CSRF 실패 JSON을 포함한 배포별 시험을 제품에 포함한다.

**개발자가 업무를 이관하기 쉽게 만드는 데 필요한 항목**

10. **반복 처리 일부가 공통 패키지 밖에 있다. 중요도 높음, 코드 확인.** [useDraftGuard](../../frontend/apps/reference-app/src/shared/useDraftGuard.ts)는 미저장 입력 보호라는 일반 기능이지만 `useReferenceRuntime`에 의존한다. 생성 앱 [NotesPage](../../templates/starter-v2/frontend/src/features/notes/NotesPage.vue)는 별도의 `window.confirm`·라우트 guard·Zod 오류 연결·mutation·Query 갱신 코드를 갖는다. 이대로 화면을 늘리면 같은 복잡한 처리를 복사할 가능성이 높다. 상태 소유권을 유지하면서 폼 검증 연결, dirty guard, 저장 후 갱신, 서버 필드 오류, 선택 변경과 오래된 응답 처리 등을 공통 composable로 제공하는 편이 제품 목적에 맞다. 한 개의 만능 CRUD 컴포넌트로 업무 로직까지 고정하지는 않는다.

11. **표준 업무지원 모듈과 레퍼런스 업무가 아직 분리되어 있지 않다. 중요도 높음, 제품 설계 필요.** 사용자·메뉴·역할 모델은 [Reference identity](../../backend/reference-app/src/main/java/dev/scframework/reference/identity/UserEntity.java)와 [MenuService](../../backend/reference-app/src/main/java/dev/scframework/reference/menu/MenuService.java)에 있다. 프런트도 REQUESTER/REVIEWER/ADMIN을 해석하고 앱 메뉴를 코드로 조립한다. 이 모델은 요구사항 예제로 적합하지만 고객의 조직·프로그램·조회/등록/승인/엑셀 권한 체계를 곧바로 표현하지는 못한다. 공통 subject·permission·menu·code 조회 계약과 고객 DB 어댑터를 제공하고, 특정 고객의 테이블이나 역할 이름은 확장 구현에 둔다. 서비스 권한과 행 단위 데이터 범위도 서버에서 검사한다.

12. **생성기는 앱 시작을 돕지만 이후 업무 추가까지 돕지는 않는다. 중요도 중간, 코드 확인.** [create-starter](../../scripts/create-starter.mjs)의 공개 옵션은 앱 이름·Java package·포트·artifact·새 경로이며 기능 생성 옵션은 없다. 한 필드 예제도 폼·라우트·API·타입·서버·DDL·테스트를 개발자가 연결해야 한다. 생성 앱 [package.json](../../templates/starter-v2/package.json)은 lint·타입·빌드 검사를 제공하지만 프런트 unit/E2E 실행 설정은 제공하지 않는다. Java 통합 테스트는 있으므로 모든 테스트가 없다는 뜻은 아니다. 목록/검색/상세/저장/충돌/권한과 관련 시험을 함께 생성하고, 생성된 코드는 읽고 수정할 수 있도록 해야 한다.

13. **초기 개발 경로가 신규 JPA 앱에 치우쳐 있다. 중요도 중간, 코드 확인.** [서버 Starter](../../backend/framework-spring-boot-starter/pom.xml)는 JPA·Querydsl·MyBatis·H2·Flyway·Feign 등을 함께 가져오며 Notes 예제도 여러 기술을 동시에 사용한다. 기존 SQL/프로시저를 유지하면서 Vue와 API부터 이관하려는 개발자는 불필요한 개념까지 먼저 익혀야 한다. MyBatis/JDBC 중심 이관 템플릿과 신규 JPA 템플릿을 같은 공통 보안·오류·트랜잭션 계약 아래 선택하도록 한다. 여러 기술을 제공하는 것과 모든 소비 앱이 같은 기술을 필수 사용하게 하는 것을 구분한다.

14. **API 타입 생성 절차가 실제 H2 서버 기동에 묶여 있다. 중요도 중간, 코드 확인.** [bootstrap-api.mjs](../../templates/starter-v2/scripts/bootstrap-api.mjs)는 새 서버를 H2 URL로 강제 기동하여 OpenAPI를 수집한다. 고객용 migration·mapper가 Oracle 등 전용이면 이 단계부터 실패할 수 있다. 계약 생성용 profile과 지원 DB의 임시 schema, 또는 검증된 명세를 사용하는 절차를 선택하도록 한다. 통합 DB 검증과 타입 생성이 필요한 범위를 분리하되 실제 API와 명세의 일치 검사는 유지한다.

15. **공통 HTTP의 안전한 확장점이 부족하다. 중요도 중간, 코드 확인.** [RequestOptions](../../frontend/packages/runtime/src/http.ts)는 취소 signal과 blob/arraybuffer만 받으며 timeout은 30초로 고정되어 있다. 응답 body만 돌려주므로 다운로드 파일명의 Content-Disposition, ETag, 업무별 헤더, 업로드 진행률 등을 공식 계약으로 사용하기 어렵다. Axios adapter로 저수준 대체는 가능하지만 일반 업무 개발자용 확장 계약은 아니다. 세션 generation·CSRF·origin 제약을 보존하는 허용 헤더, 요청별 timeout, 응답 metadata, 업로드 옵션을 검토한다. 장시간 배치에는 무제한 timeout보다 작업 등록·상태 조회 방식이 적합하다.

16. **일반 표와 대량 편집 업무 그리드의 범위를 구분해야 한다. 중요도 고객 요구에 따름.** [표 공개 계약](../../frontend/packages/ui/src/table/contracts.ts)은 선택·정렬·페이지·셀 slot·가상화를 제공한다. 다중 셀 편집/붙여넣기, 변경 행 추적, 묶음 저장, 컬럼 폭·고정·사용자 설정 저장은 해당 공개 계약에서 확인되지 않았다. slot으로 구현할 수 있다는 사실과 제품이 제공한다는 사실은 다르다. 고객의 대표 입력 화면으로 필요한 범위를 결정하고, 편집 그리드가 필요하면 별도 선택 모듈로 제공한다. 가상화만으로 서버 조회·파일 생성·브라우저 메모리 사용까지 해결되는 것은 아니다.

17. **고객별 테마 설정의 공식 진입점이 제한적이다. 중요도 중간, 코드 확인.** [ScVuetifyOptions](../../frontend/packages/ui/src/theme.ts)는 locale/fallback만 받고 색은 공통 `uiTokens`를 사용한다. CSS 변수나 반환된 Vuetify를 이용한 조정 자체가 불가능한 것은 아니지만, 고객 테마를 안정적으로 적용하는 공식 계약은 부족하다. 공통 소스를 고객별로 수정하는 대신 앱 단위 브랜드·로고·색·밀도 설정을 지원하고 접근성 검사를 함께 제공한다.

**현재 환경에서 재현한 결함과 출시 운영 과제**

18. **Windows에서 의존성 경계 검사기가 위반을 놓친다. 중요도 높음, 실제 재현.** [check-ui-boundaries.mjs](../../scripts/check-ui-boundaries.mjs)는 OS 경로로 만든 값에 `file.startsWith(packages + "/")` 등을 사용한다. Windows 역슬래시 경로에서는 공통/소비 앱 판정이 false가 되어, 비공개 패키지 import·공통에서 앱 import·다른 앱 import가 모두 exit 0으로 통과했다. npm exports나 다른 검사가 모든 실제 import까지 허용한다는 의미는 아니며, 이 아키텍처 검사 자체가 보증하지 못한다는 결함이다. `path.relative` 등 OS 독립 판정으로 수정하고 Windows/Linux에서 위반을 실제 거절하는 시험을 CI에 포함해야 한다.

19. **생성 앱의 통합 테스트 초기화는 Windows에서 실패할 경로가 있다. 중요도 높음, 원인 API 재현.** [GeneratedAppIntegrationTest](../../templates/starter-v2/backend/src/test/java/__JAVA_PATH__/GeneratedAppIntegrationTest.java) 38행과 [GeneratedOperationsIntegrationTest](../../templates/starter-v2/backend/src/test/java/__JAVA_PATH__/GeneratedOperationsIntegrationTest.java) 73행은 조건 없이 POSIX 권한을 설정한다. 현재 Windows 파일시스템에서 같은 호출은 UnsupportedOperationException을 냈다. 생성 앱 전체 테스트 실행 결과는 아니지만 초기화 코드의 비호환 원인은 재현했다. OS별 private file 처리와 테스트 fixture를 제공하고, generated 앱의 설치→빌드→실행까지 Windows CI로 확인해야 한다. 분석 중 루트에 Windows `dev.mjs`/`dev.ps1` 추가 변경이 관찰되었으므로 루트 실행기 전체를 미지원이라고 판정하지 않는다. 생성 템플릿의 Bash 중심 절차와 별개의 문제다.

20. **출시 버전과 고객 업그레이드 계약을 더 정리해야 한다. 중요도 중간, 코드 확인.** 현재 npm은 0.3.0, Maven은 0.3.0-SNAPSHOT이며 [pack 스크립트](../../scripts/package-framework.mjs)는 서버 버전에 SNAPSHOT 대응을 요구한다. 해시를 고정한 오프라인 배포 세트의 장점은 있으나, 장기 고객 공급에는 불변 release 좌표·변경 이력·지원 조합·보안 패치 절차가 필요하다. 생성기는 기존 고객 코드를 병합하지 않으며 [upgrade 검증 스크립트](../../scripts/verify-package-upgrade.py)는 특정 외부 fixture 경로에 제한된다. 범용 고객 업그레이드 도구로 보아서는 안 된다. 공통 운영 DDL도 템플릿에 복사되므로 프레임워크 업그레이드 시 고객 migration과 버전 충돌 없이 적용할 절차가 필요하다. 이전 패키지로 돌아가는 것과 변경된 DB·업무 데이터를 복원하는 것은 구분한다.

21. **소비자 문서에 현재 상태 불일치가 있다. 중요도 중간, 코드 확인.** [runtime README](../../frontend/packages/runtime/README.md)는 현재 버전을 0.2.0으로 설명하지만 package.json은 0.3.0이다. [생성 템플릿 README](../../templates/starter-v2/README.md)에는 v2 검사가 작성 단계라고 남아 있으나 루트 문서는 과거 독립 소비 검증 완료를 기술한다. 과거 기록은 유지하되 고객용 현재 사용법·지원 범위·검증 상태를 한곳에서 읽을 수 있게 분리해야 한다. JSP 개발자용 설명 주석은 장점이지만 긴 변경 이력과 고급 기술이 첫 개발 안내를 가리지 않도록 한다.

22. **배포와 운영 지원 범위를 제품 옵션으로 확정해야 한다. 중요도 고객 요구에 따름.** 기본은 파일 H2·로컬 파일·서버 세션이고 runtime 파일 잠금도 있다. 여러 앱 인스턴스를 운영하려면 DB·파일·세션·스케줄러·중복 처리에 대한 별도 토폴로지와 장애 검증이 필요하다. Redis 없이도 [Spring Session JDBC](https://docs.spring.io/spring-session/reference/http-session.html) 같은 선택지는 있으나 현재 구현에 추가됐다는 뜻은 아니며 구형 세션의 자동 호환도 보장하지 않는다. 지원하지 않을 경우 단일 인스턴스라는 제품 범위를 명확히 해야 한다. 생성 vendor 폴더는 공통 배포물 중심이며 모든 npm/Maven 외부 의존성을 포함한 폐쇄망 설치 완료를 의미하지 않는다. private/UNLICENSED 표시는 공개 npm 게시를 의도하지 않는 현재 상태이며 판매 불가능이라는 결론은 아니다. 고객 제공 파일·외부 의존성 고지·패치 전달·지원 조건을 출시 체크에 포함한다.

**프레임워크로 제공할 구조**

현재 공통 패키지 경계를 유지하면서 반복되는 기능을 다음과 같이 제품으로 제공하는 방향이 적합하다. 아래 이름은 제안이며 현재 존재하는 패키지 목록은 아니다.

| 제공 영역           | 프레임워크가 책임질 것                           | 소비 앱이 책임질 것                    |
| ------------------- | ------------------------------------------------ | -------------------------------------- |
| UI와 업무 화면 패턴 | 검색·목록·상세·폼·편집 그리드·오류·접근성        | 업무 필드·배치·계산·상태 전이          |
| 폼과 조회 로직      | dirty guard·검증 연결·동시 저장·Query 갱신       | 검증 schema·API 함수·업무 승인 규칙    |
| identity와 권한     | subject·permission·menu·행위 검사 계약           | 기존 사용자/조직 DB 어댑터·데이터 범위 |
| 데이터 접근         | 지원 DB별 공통 저장소·트랜잭션 연결·이관 profile | 기존 SQL·프로시저·업무 schema          |
| 레거시 연결         | gateway 계약·오류 변환·인코딩·timeout·추적       | 기존 JSP/EJB가 제공할 업무 인터페이스  |
| 파일과 운영         | 저장소 인터페이스·감사·스케줄·작업 상태          | 파일 권한·보존 정책·업무 batch         |
| 개발 도구           | 앱/기능 생성·계약 검사·실패 예제·업그레이드 안내 | 생성 후 업무 구현·고객별 배포 설정     |

공통 기능을 고객마다 복사해서 만드는 비용을 줄이는 것이 기준이다. 동시에 고객 업무 규칙을 공통 core에 넣어 다른 고객에게 영향을 주지 않도록 한다. 확장점만 선언하고 구현·예제·테스트를 고객에게 모두 떠넘기는 방식도 제품 목적에 충분하지 않다.

**JSP와 EJB를 옮기는 표준 절차**

| 기존 코드                     | 이관 위치                               | 반드시 비교할 것                        |
| ----------------------------- | --------------------------------------- | --------------------------------------- |
| JSP HTML·JSTL 표시            | Vue template·공통 UI                    | 값 표시·조건·접근성·인쇄                |
| JSP scriptlet의 업무 계산     | 서버 ApplicationService/Service         | 반올림·상태 전이·오류와 예외            |
| JSP JDBC·SQL·프로시저 호출    | MyBatis/JDBC 어댑터                     | 파라미터·정렬·null·잠금·성능            |
| session 속성 기반 사용자/권한 | 인증 어댑터·서버 권한 검사              | 만료·권한 변경·조직별 조회 범위         |
| EJB 메서드와 CMT              | 기존 서비스 gateway 또는 이식한 Service | commit·rollback·전파·재시도·중복        |
| 서버 파일 경로                | 파일 저장소·metadata 어댑터             | 첨부 연결·권한·해시·복구                |
| submit·redirect·팝업          | Router·폼·확인 대화상자                 | 뒤로가기·새로고침·중복 저장·미저장 입력 |

첫 단계는 화면을 새로 그리는 것이 아니라 한 업무의 기존 동작을 입력·출력·DB 변화·권한·트랜잭션 단위로 기록하는 것이다. 익명화한 동일 사례로 구형 결과를 보존하고 새 구현과 대조한다. 브라우저 표시 로직만 Vue로 옮기고, 최종 업무 계산·권한·데이터 변경은 서버에서 실행한다.

병행 운영은 기존 WAS와 새 Spring 앱을 분리하고, reverse proxy가 기능별로 요청을 전달하는 구성이 검토 출발점이다. Vue의 공통 client는 새 서버 API를 사용하고 새 서버의 업무 어댑터가 구형 서비스와 통신한다. 기능별 쓰기 소유권을 정해 옮기며 구형 서버가 이미 완료한 변경을 새 서버의 예외만으로 되돌릴 수 있다고 가정하지 않는다. 원격 호출 timeout은 업무 실패 확정을 뜻하지 않을 수 있으므로 요청 식별·상태 조회·중복 방지를 함께 설계한다.

**개선 순서와 완료 조건**

| 순서 | 작업                                | 완료 조건                                                                                 |
| ---- | ----------------------------------- | ----------------------------------------------------------------------------------------- |
| 1    | 지원 환경과 이관 방식 확정          | 대상 DB/WAS/Java·OS·배포 경로·계정·EJB 트랜잭션·대표 업무를 적은 지원표                   |
| 2    | 확인된 Windows 결함과 URL 보안 보완 | 금지 import 3종 거절, generated 앱 실제 빌드, 비API 업무 URL의 미인증·무권한 거절         |
| 3    | DB와 레거시 어댑터의 첫 구현        | 목표 DB에서 공통 운영 기능, 기존 SQL/계정 연결, `/erp/` 직접 접근·재로그인·오류 처리 통과 |
| 4    | 공통 폼 로직과 기능 생성            | 고객 앱이 reference-app import 없이 목록·상세·저장·409·dirty 보호와 테스트를 생성·사용    |
| 5    | 대표 업무의 동작 보존 검증          | JSP 복합 검색 1개, 다중 테이블 저장/EJB 업무 1개, 첨부 또는 대량 입력 1개를 신구 비교     |
| 6    | 고객 독립 배포와 업그레이드         | 새 경로의 앱을 지정 OS·DB에서 설치·빌드·운영하고 고객 변경을 보존한 패치 적용과 복구 시험 |

대표 업무 검증에서는 성공 화면 외에도 중간 DB 실패·동시 수정·권한 변경·세션 만료·한글/날짜/금액·기존 첨부·대량 조회를 포함한다. 성능 목표와 데이터량은 고객 환경에서 정하며 근거 없는 공통 처리량을 약속하지 않는다. 데이터 쓰기가 시작된 이후의 복귀에는 업무 데이터 정합성 절차가 필요하므로 단순 이전 JAR 교체만으로 완료하지 않는다.

현재 코드를 전면 폐기할 이유는 없다. UI·runtime·서버 Starter의 기존 분리를 기반으로, 목표 DB와 기존 인증·트랜잭션을 연결하는 실제 이관 패키지, 반복 업무 생성, 독립 소비 검증을 강화하는 것이 제품 목적에 직접 연결된다.
